Engine Hardening: Preset Negotiation + Agent Payment Permission

오늘의 핵심은 협상 엔진이 자연어 대화를 구조화해 조건을 모으고, 결제 단계에서는 사용자가 승인한 규칙만 x402, Stripe, 스마트 컨트랙트에 전달하도록 만드는 것이다.

1. 목표 아키텍처

목표는 협상 엔진이 대화를 그냥 저장하는 것이 아니라, 상품별로 실행 가능한 조건으로 바꾸고, 사용자가 승인한 조건만 결제와 스마트 컨트랙트에 전달하는 구조를 만드는 것이다. 핵심 원칙은 대화는 조건 후보, 사용자 확인은 권한, 온체인 receipt는 최종 사실로 나누는 것이다.

Target System Map
Input 사용자 + 상품 + 판매자 링크 대화, 상품 스펙, 판매자 조건, 기존 메모리를 함께 받는다.
->
Engine 대화를 실행 조건으로 구조화 Tag Garden이 term을 만들고, 부족한 조건은 질문/UI control로 채운다.
->
Permission 사용자 확인 후 권한 고정 AgentPaymentGrant와 approval_policy_hash로 결제 가능 범위를 잠근다.
->
Execution x402 우선 + Stripe fallback + Contract funding, release, receipt 확인을 분리하고 최종 사실만 상태에 반영한다.
Order + Branch Flow
1. 대화/상품 입력 사용자 말, 상품명, 판매자 링크, 기존 메모리, 현재 listing을 같이 본다.
->
관련 없음 / 공격성 / 인젝션 협상 조건으로 저장하지 않고 안전하게 무시하거나 다시 묻는다.
관련은 있지만 부족함 필수 tag와 애매한 숫자, 제품 차이를 Gap Panel로 보낸다.
충분히 구조화 가능 Preset draft와 협상 전략 후보를 만든다.
->
2. 사용자 조정/확인 slider, toggle, select, 직접 입력으로 조건을 한 번에 수정하고 필수 term을 확정한다.
3. Permission Gate 사용자가 확인한 term만 결제 권한 후보가 된다.
->
확인 안 됨 AgentPaymentGrant를 만들지 않고 협상/질문 단계로 되돌린다.
확인됨 상품, 판매자, cap, rail, 필수 term, 만료 시간을 hash로 고정한다.
->
4. AgentPaymentGrant approval_policy_hash가 x402 requirement, Stripe metadata, contract signature의 공통 기준이 된다.
5. Payment Rail x402를 우선 사용하고, 카드/온램프가 필요하면 Stripe fallback으로 간다.
->
x402 + smart contract createAndFund() -> funding receipt -> release 조건 -> release receipt -> SETTLED
Stripe fallback 같은 policy hash를 metadata에 묶고 webhook/receipt로 상태를 확정한다.
->
6. Final State funding은 “자금 잠김”, release receipt 성공만 “판매자 지급 완료”로 기록한다.
Negotiation Engine Map
Haggle Negotiation Engine 엔진의 역할은 “답변을 잘하는 것”이 아니라, 상품별 협상과 결제가 가능한 조건 세트를 안전하게 만드는 것이다.
A. Context Router 이 말이 현재 상품 협상에 연결되는지 먼저 판단한다.
->
무관한 말 메모리에 저장하지 않고 대화만 자연스럽게 이어간다.
상품이 다름 기존 메모리와 현재 listing의 차이를 물어본다.
현재 협상과 관련 있음 Tag Garden으로 보낸다.
->
필수 tag 부족 질문 또는 조정 UI를 띄운다. 예: 배터리 기준, price cap, 모델 범위.
협상 시작 가능 preset 전략을 적용하고 판매자 메시지/offer를 생성한다.
1. Intent + Context Router 사용자 말이 예산인지, 모델명인지, 조건인지, 무관한 잡담인지 구분하고 상품/판매자/메모리와 연결한다.
2. Tag Garden Builder 배터리 기준, 가격 cap, 제품 차이, 필수 확인값을 태그로 만들고 binary, slider, select, 직접 입력 UI 타입을 정한다.
3. Gap + Question Planner 필수 term이 없으면 협상 시작을 막고, 자연스러운 질문이나 한 번에 고칠 수 있는 조정 패널로 부족분을 채운다.
4. Preset Strategy Tuner Deal maker, fast close, strict cap 같은 preset이 실제로 다른 opening offer, 양보 폭, 질문 순서를 내도록 조정한다.
Safety layer: 프롬프트 인젝션, 무관한 발화, 상품 불일치, 메모리 오용, 결제 권한 초과를 모든 단계에서 차단한다. 메모리는 추천 근거일 뿐이고, 결제 권한은 사용자가 확인한 term에서만 만들어진다.
1. Conversation Intake 사용자 말, 상품 정보, 판매자 링크, 기존 메모리를 받는다. 이상한 말이나 공격성 문장은 저장 대상에서 제외하고, 필요한 조건 후보만 뽑는다.
2. Tag Garden 배터리, 가격 상한, 제품 모델, 배송 방식처럼 협상에 필요한 term을 태그로 구조화한다. 필수 태그는 누락되면 질문하거나 UI에서 강제한다.
3. Preset Tuning 엔진이 추천 전략을 만들고 사용자는 cap, opening offer, 필수 확인 조건, 타협 범위를 한 화면에서 고친다.
4. Payment Grant 사용자가 승인한 조건만 AgentPaymentGrant로 고정한다. 이때 approval_policy_hash가 x402, Stripe, 컨트랙트의 공통 기준이 된다.
5. Settlement Execution x402가 우선이고 Stripe는 fallback이다. 스마트 컨트랙트는 funding, release, receipt 확인을 분리해 실제 지급 완료 시점만 SETTLED로 기록한다.

쉽게 말하면, Haggle은 “대화를 결제 가능한 정책으로 번역하는 엔진”이고, 결제 시스템은 그 정책을 벗어나지 못하게 잠그는 실행 레이어다. 엔진이 더 똑똑해질수록 바뀌는 것은 결제 권한 자체가 아니라, 권한을 만들기 전에 어떤 조건을 묻고 어떤 전략을 추천하는지다.

Engine Improvement Cycle
1. 디자인 사용자 경험 기준을 먼저 정한다. 예: 부족한 조건을 한 번에 보여주고, control 타입을 조건 성격에 맞춘다.
->
2. 설계 엔진이 어떤 branch와 blocker를 만들어야 하는지 정의한다. 예: 관련 없음, 정보 부족, 상품 불일치, 협상 시작 가능.
->
3. 구현 서비스, API schema, UI, 테스트에 같은 구조를 연결한다.
4. 리뷰 타입체크, 테스트, 데모 화면 기준으로 빠진 branch와 잘못된 상태 전환을 찾는다.
->
고칠 점 있음 수정 후 다시 리뷰한다. 이 루프는 완료 기준을 만족할 때까지 반복한다.
완료 기준 만족 오버뷰에 결정, 구현, 검증 결과를 남기고 다음 사이클로 넘어간다.
->
5. 완료 코드와 문서가 같은 흐름을 설명하고, 다음 구현 후보가 명확한 상태다.
레이어책임실패하면 안 되는 것
대화 이해 사용자 의도, 상품 차이, 부족한 조건, 공격성/무의미 입력을 구분 “17” 같은 숫자를 제품 모델인지 가격인지 문맥 없이 확정하지 않기
Tag Garden 조건을 binary, slider, select, 직접 입력 등 알맞은 UI 타입으로 표현 필수 조건이 비어 있는데 협상을 시작하지 않기
Preset Model 가격 cap, 시작 제안, 양보 폭, 질문 우선순위를 상품별로 조정 모든 preset이 같은 결과를 내지 않게 만들기
Permission 사용자가 확인한 조건만 AgentPaymentGrant와 hash로 고정 메모리나 대화 초안만으로 결제 권한을 만들지 않기
Payment + Contract x402 우선 결제, Stripe fallback, 조건부 settlement, receipt 확인 funding 제출을 판매자 지급 완료로 오해하지 않기

3. 오늘 리뷰하고 고친 점

문제수정의미
조건부 정산 컨트랙트 주소가 API quote에 연결되지 않음 HAGGLE_CONDITIONAL_SETTLEMENT_ADDRESS를 읽어 quote metadata에 address와 capability를 싣도록 연결 프론트/지갑이 이 결제가 rules-limited settlement를 지원하는지 알 수 있다.
x402 exact transfer를 컨트랙트 주소로 바로 보내면 내부 기록 없이 토큰만 들어갈 위험 기본값은 metadata-only로 두고, exact receiver가 조건부 정산 컨트랙트와 같으면 seller wallet로 되돌리도록 차단 컨트랙트의 createAndFund()가 호출되지 않는 잘못된 입금을 피한다.
조건부 정산 signer가 없어서 정책 해시를 온체인 서명에 묶을 수 없었음 approval_policy_hash, agreement_hash, listing_hash, grantNonce를 EIP-712 메시지에 포함 다른 상품, 다른 합의, 다른 결제 권한으로 서명을 재사용하기 어렵다.
구매자 지갑이 컨트랙트를 호출할 준비 payload가 없었음 POST /payments/:id/x402/conditional-settlement-request 추가 서버가 자금을 움직이지 않고, 구매자 지갑이 서명된 createAndFund() 파라미터를 받아 실행할 수 있다.
엔진이 협상을 시작해도 되는지 스스로 리뷰하는 구조가 부족했음 PresetTuningDraft.engineReview 추가: scope conflict, missing hard terms, next controls, branch outcome을 생성 “MacBook 기억을 iPhone 상품에 적용해도 되는가”, “배터리 기준을 slider로 물어야 하는가” 같은 판단을 UI와 결제 권한 전에 확인할 수 있다.
엔진 리뷰가 화면에는 보이지만 실제 협상 실행 gate에는 완전히 묶이지 않았음 engineReview.status !== ready이면 자동 협상 시작을 막고, 첫 blocker 또는 next action 질문을 start blocked reason으로 표시 디자인 문서의 Permission Gate가 실제 데모 실행 경로에도 적용되어, 필수 term이 비어 있거나 상품 scope가 충돌하면 협상이 시작되지 않는다.
gate가 막은 뒤 사용자가 blocker를 해소하는 경로가 부족했음 상품 scope 충돌 next action에 현재 상품에 적용 버튼 추가. 클릭하면 scope blocker를 제거하고 branch outcome을 다시 계산 엔진 고도화 사이클이 “막기”에서 끝나지 않고, 수정 후 다시 리뷰해서 완료될 때까지 반복되는 구조가 UI에 생겼다.
missing hard term은 Required checks까지 내려가서 따로 찾아 눌러야 했음 Next controls의 term action에 확인됨으로 표시 버튼 추가. 클릭하면 해당 term을 checked 처리하고 engineReview를 다시 계산 엔진이 “무엇이 부족한지”를 보여준 자리에서 바로 수정과 재리뷰가 가능해져, 사이클이 더 짧아진다.
Next controls가 slider/select/toggle/text 타입을 말하지만 화면에서는 모두 같은 확인 버튼처럼 보였음 각 action에 controlConfig를 추가하고, UI에서 배터리는 slider, IMEI/lock은 toggle, scope/storage는 select, cycle count는 text로 입력받게 수정 “배터리 90% 이상” 같은 값은 숫자로, “Find My off” 같은 조건은 yes/no로 받아 협상 payload의 의미가 더 선명해진다.
API 전체 타입체크에서 dispute webhook outbox payload 타입 경계가 좁게 잡혀 있었음 DB row를 outbox record로 돌려줄 때 payload JSON 타입 경계를 명시적으로 통과하도록 캐스팅을 정리 이번 엔진 변경과 별개로 전체 API 타입체크를 다시 녹색으로 맞췄다.
사용자가 slider/select/toggle/text로 넣은 값이 rationale 문장에는 남지만 구조화된 term 값으로는 남지 않았음 PresetTermDraft.confirmedValue 추가. 값, label, unit, source를 listing evidence와 user input 모두에 저장 “배터리 90%”, “Activation Lock off”, “cycle count 720” 같은 조건이 다음 협상, memory card, payment grant payload에서 재사용 가능해진다.
저장된 user-tuned preset을 다시 적용할 때 checked 여부만 복원되고 실제 확인값은 draft로 돌아오지 않았음 memory card의 checkedTerms.confirmedValue를 termId별 map으로 읽고, draft 적용 시 term의 confirmedValue로 복원 이전에 확인한 “90%”, “Unlocked”, “720 cycles” 같은 값이 다음 협상 화면과 payload에 그대로 유지된다.
저장된 확인값을 복원할 때 현재 listing의 실제 evidence와 충돌해도 덮어쓸 위험이 있었음 candidate value와 현재 term의 listing-source confirmedValue가 다르면 current listing 값을 유지 예전 preset의 “battery 90%”가 현재 listing의 “battery 86%”를 덮지 못해 협상 근거가 더 정확해진다.
충돌한 저장값을 건너뛰어도 사용자는 왜 preset 값이 적용되지 않았는지 알기 어려웠음 Saved preset value skipped strategy note를 만들고, applied tuned preset 카드에 충돌 term과 listing 값을 표시 자동 적용이 조용히 실패하지 않고, 사용자가 “저장된 90% 대신 listing 86%를 썼다”는 이유를 바로 볼 수 있다.

이번 추가 사이클은 디자인 → 설계 → 구현 → 리뷰 → 수정 → 다시 리뷰로 진행했다. 리뷰 중 타입 경계에서 pendingSlots가 빠져 있는 문제와 blocker source 타입이 좁은 문제가 발견되어 수정했고, 이후 API 테스트와 web/API typecheck를 다시 통과시켰다. 이어진 추가 사이클에서는 engineReview를 실행 gate에 연결했고, 리뷰 단계에서 web/API typecheck와 preset 테스트를 다시 통과시켰다. 이번 사이클에서는 gate resolution control을 추가했고, web typecheck와 preset 테스트로 다시 리뷰했다. 다음 사이클에서는 missing hard term을 Next controls에서 바로 확인 처리하도록 연결했고, 다시 web typecheck와 preset 테스트를 통과시켰다. 이번 추가 사이클에서는 Next controls를 실제 typed input으로 바꾸고, API 전체 타입체크에서 발견된 outbox 타입 경계까지 수정했다. 이어진 사이클에서는 typed input의 결과를 confirmedValue로 구조화해 저장하고, preset 저장 카드에도 확인값이 남도록 했다. 이번 사이클에서는 저장된 confirmedValue를 다시 draft에 복원하고, Required checks에서 확인값 badge를 볼 수 있게 했다. 이어서 저장값과 현재 listing evidence가 충돌할 때는 listing 값을 우선하는 규칙을 추가했다. 이번 사이클에서는 그 충돌 규칙을 화면에 설명해, 건너뛴 저장값이 applied tuned preset 카드에 드러나게 했다.

4. 사용자에게 설명할 예시

예시: iPhone 협상 1. 사용자가 "최근 3년 이내 아이폰, 배터리 90% 이상, 예산 $450"이라고 말한다. 2. 엔진은 "iPhone / battery >= 90 / price cap 450 / seller/listing fixed"로 조건을 구조화한다. 3. 사용자는 preset panel에서 cap, opening offer, 필수 확인 조건을 한 번에 수정한다. 4. 결제 직전 AgentPaymentGrant가 만들어지고 approval_policy_hash가 고정된다. 5. x402 requirement, Stripe metadata, conditional settlement signer가 같은 hash를 공유한다. 6. 구매자 지갑은 conditional-settlement-request의 서명된 payload로 createAndFund()를 호출한다. 7. 블록 receipt가 확인되면 배송과 release 준비가 열리고, 판매자 지급은 release 조건이 끝난 뒤 별도 release tx로 확정된다.

5월 5일 추가 구현: 구매자 결제 화면은 quote 이후 조건부 정산 요청을 받아오고, 응답이 있으면 USDC approve 대상을 조건부 정산 컨트랙트로 바꾼다. 마지막 단계에서는 기존 exact x402 payload 대신 지갑에서 createAndFund()를 호출한다. 조건부 정산 요청이 준비되지 않은 환경에서는 기존 x402 submit 흐름으로 fallback한다. 지갑이 funding 트랜잭션을 제출하면 /payments/:id/x402/conditional-settlement-funding로 tx hash를 기록하고, 결제 상태는 판매자 지급 완료가 아닌 SETTLEMENT_PENDING으로 전환한다. 이어서 /payments/:id/x402/conditional-settlement-confirmation이 Base RPC에서 receipt를 확인해 성공이면 FUNDING_CONFIRMED, 실패면 FUNDING_FAILED로 기록한다. funding이 확인된 시점에는 판매자 지급 완료로 보지 않지만, 자금은 컨트랙트에 잠겼으므로 shipment와 settlement release 준비는 시작한다. release는 현재 컨트랙트가 부분 지급이 아니라 전체 settlement 지급만 지원하므로, FULLY_RELEASED 단계에서만 /settlement-releases/:id/conditional-release-request가 seller/fee split이 들어간 EIP-712 Release payload를 만든다. 이후 운영자/relayer가 release()를 제출하면 /settlement-releases/:id/conditional-release-execution이 release tx hash를 저장하고, /settlement-releases/:id/conditional-release-confirmation이 receipt를 확인해 성공 시 payment intent를 최종 SETTLED로 전환한다. 실패 receipt는 결제를 실패 처리하지 않고 release 재시도 가능한 상태로 남긴다.
