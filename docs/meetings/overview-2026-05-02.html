Preset Negotiation Models + Term Garden

상품을 누르고 프리셋과 가격 캡만 정하면, 상품 태그별 조건(term)을 자동으로 채운 협상 전략 초안을 만들고 사용자가 필요한 값만 조정한 뒤 바로 협상을 시작하는 구조를 설계한다.

작성일: 2026-05-01 브리핑 대상일: 2026-05-02 브랜치: engine-hardening
🎯핵심 방향

지금까지는 Advisor Engine이 대화로 부족한 조건을 하나씩 물어보는 흐름이었다. 다음 단계는 사용자가 상품을 선택하면 엔진이 협상 모델을 한 번에 제안하고, 사용자는 UI에서 필요한 항목만 고치는 방식으로 바꾸는 것이다.

원칙: 자동 기억은 추천값을 만들고, 실제 협상 실행은 사용자가 승인한 프리셋 튜닝 초안을 기준으로 한다. 상품 정보는 사용자가 누른 listing이 source of truth이고, 가격 캡은 절대 넘지 않는 hard invariant다.
🧩구현 계획

구현은 Preset, Tag Term Requirement, Draft Compiler, Developer Demo UI, Negotiation Start Payload 순서로 쌓는다.

1. Negotiation Preset

Strategy Template

협상 스타일의 기본값이다. 예: Safe Buyer, Balanced Closer, Lowest Price, Fast Close, Condition Leverage.

  • opening strategy
  • concession speed
  • risk tolerance
  • walk-away style

2. Tag Term Requirement

Term Garden

상품 태그별로 협상에 필요한 조건을 제공한다. iPhone이면 배터리, 통신사 잠금, Find My 같은 term이 자동 후보가 된다.

  • hard / soft / deal breaker
  • preset별 적용 여부
  • 질문 문구와 UI label
  • 협상 leverage 연결

3. Draft Compiler

Listing + Memory + Preset

선택 상품, 프리셋, 가격 캡, 사용자 기억, tag terms를 합쳐 수정 가능한 협상 초안을 만든다.

  • opening offer 계산
  • must verify 체크리스트 생성
  • leverage point 추천
  • walk-away rule 생성

4. Negotiation Start Payload

Execution Contract

협상 시작 시 listing, preset, tuning draft, cap, memory snapshot을 함께 넘긴다.

  • listing은 기준 사실
  • cap은 절대 상한
  • draft는 사용자 승인 전략
  • memory는 보조 맥락
User clicks listing → selects preset → enters price cap → compiler creates tuning draft → user edits checklist/sliders/chips → start negotiation with listing + preset + cap + draft + memory
🏷️Tag별 Term 설계

Term Garden은 질문만 만드는 시스템이 아니라, 협상 전략 초안의 체크리스트, 가격 인하 근거, 중단 조건을 제공하는 term provider가 된다.

TagTerms협상에 쓰이는 방식
electronics/phones/iphone battery_health, carrier_lock, find_my_off, storage_capacity, screen_condition 배터리가 기억 기준보다 낮으면 가격 인하 근거. Find My on 또는 carrier locked는 Safe Buyer에서 walk-away 후보.
vehicles/tesla mileage, accident_history, battery_degradation, title_status, charging_cable 사고/타이틀/배터리 리스크가 있으면 보수적으로 시작하거나 검증 전 협상 중단.
laptop/macbook battery_cycle_count, keyboard_condition, applecare_status, storage_capacity, screen_condition 휴대성/배터리 기억과 연결. cycle count가 높거나 AppleCare 없음은 leverage point.
type TagTermRequirement = { tag: string; termId: string; label: string; enforcement: "hard" | "soft" | "deal_breaker"; question: string; appliesToPresets: string[]; defaultImportance: "low" | "medium" | "high"; evidenceSource: "listing" | "memory" | "user" | "seller_reply"; }
🕹️Preset Tuning UI

챗봇이 하나씩 묻는 대신, 엔진이 협상 전략을 한 번에 제안하고 사용자가 UI에서 값을 고친다.

Safe Buyer 예시

iPhone 15 Pro

상품: iPhone 15 Pro, ask $500, battery 86%, unlocked

  • Price cap: $450
  • Opening offer: $385
  • Must verify: battery, Find My off
  • Leverage: battery below preferred 90%
  • Walk away: Find My on, seller refuses battery info

Lowest Price 예시

Condition Leverage

상품 상태와 시세 차이를 가격 인하 근거로 적극 사용한다.

  • Opening offer: ask보다 낮게 anchor
  • Concession: slow
  • Leverage: visible wear, missing accessories
  • Walk away: cap 초과 요구

Fast Close 예시

Speed First

좋은 가격이면 빠르게 합의하지만 cap은 넘지 않는다.

  • Opening offer: cap에 가까운 합리적 제안
  • Concession: fast
  • Must verify: deal breaker만 확인
  • Walk away: seller slow response 또는 cap 초과

💳Agent Payment Permission Layer

협상 엔진이 결제를 직접 움직이는 구조가 아니라, 사용자가 승인한 조건을 AgentPaymentGrant로 고정하고 x402, Stripe, 온체인 정산이 같은 정책 해시를 확인하는 구조로 강화한다.

1. AgentPaymentGrant

Buyer-approved Rules

상품, 판매자, 금액 상한, 허용 rail, 만료 시간, 필수 term을 하나의 결제 권한 단위로 저장한다.

  • max_amount_minor는 절대 상한
  • listing_id, seller_id로 재사용 제한
  • terms는 Tag Garden에서 온 조건
  • human_confirmation_required로 사람 확인 여부 분리

2. Policy Hash

Audit Binding

승인 조건만 canonical JSON으로 정렬한 뒤 approval_policy_hash를 만든다. 랜덤 grant_id나 nonce는 제외해 재시도해도 같은 조건은 같은 정책으로 남긴다.

  • 조건 바꿔치기 방지
  • 다른 상품에 권한 재사용 방지
  • webhook에서 hash mismatch 차단
  • 향후 스마트 컨트랙트 인자로 확장

3. Legal-safe Terms

Terminology Guard

제품 문구는 custody, deposit, guaranteed safe 같은 표현을 피하고 buyer-approved authorization, conditional settlement, rules-limited settlement를 사용한다.

  • 자금 보관 사업처럼 보이지 않게 설계
  • USDC는 투자상품이 아니라 결제 수단으로 표현
  • Stripe fallback도 같은 정책 검증 통과
Negotiation accepted → AgentPaymentGrant created → approval_policy_hash + agreement_hash + listing_hash → x402 requirement extra / Stripe metadata → quote exposes conditional settlement capability → explicit receiver or contract-call path → release/refund rules in later contract phase
구현됨설명다음 단계
AgentPaymentGrant 결제 권한 모델, term tag, 법적 acknowledgement, canonical policy JSON을 추가했다. 사용자가 한 화면에서 cap/term을 수정하고 명시적으로 승인하는 UI 연결.
x402 requirement grant_id, approval_policy_hash, agreement_hash, listing_hash를 extra에 넣는다. 실제 x402 client signing과 contract-call 또는 deterministic receiver 방식 연결.
Stripe metadata Stripe onramp/session에도 같은 hash를 넣고 webhook에서 mismatch를 막는다. Stripe manual capture 또는 agentic payment token 구조와 비교 검토.
Receiver selection x402 exact payment는 명시적인 HAGGLE_X402_PAYMENT_RECEIVER_ADDRESS가 있을 때만 seller wallet 외 주소를 사용한다. 조건부 정산 컨트랙트는 direct ERC-20 transfer가 아니라 contract-call 또는 dedicated receiver/sweep 방식으로 연결한다. contract 내부 기록 없이 토큰만 들어가는 상황은 피한다.
HaggleConditionalSettlement buyer가 직접 fund하고, release/refund는 policy-bound EIP-712 signature 또는 만료 조건으로만 움직인다. admin은 임의 출금 권한이 없다. ABI, EIP-712 타입, viem adapter, deploy script, API quote metadata, conditional settlement signer가 추가됐다. 기본값은 metadata-only이고, 서버 실행은 명시 플래그가 있을 때만 켠다.

5/1 구현 메모: API에 preset tuning draft compiler와 demo endpoint를 추가했고, Developer Demo에는 preset, price cap, opening offer, required checks, leverage chips, walk-away rules를 한 화면에서 조정하는 패널을 붙였다. 자동 협상 시작 시 선택 상품, 사용자 메모리, 승인된 draft, cap이 함께 init payload로 들어간다. 사용자가 조정한 draft는 advisor:preset_tuning:<scope> 메모리 카드로 저장되어 다음 상품 협상에서 user-tuned preset 후보로 회수된다. 저장된 후보는 현재 선택 상품의 listing id, title, tag, category와 점수화해 가장 가까운 후보를 먼저 추천하고, 사용자가 적용할 때 draft에 반영한다. 단, preset 후보의 cap $300 같은 요약값은 일반 예산 기억으로 승격하지 않는다. 추천용 메모리와 기본 구매 의도 메모리를 분리해, 길어진 대화나 여러 상품의 후보가 쌓여도 검색 쿼리와 예산 판단이 흔들리지 않게 했다. 같은 listing 또는 충분히 높은 점수의 후보는 기본 draft에 자동 적용하되, 사용자가 preset, cap, checklist를 직접 고치면 자동 덮어쓰기는 멈춘다. 예를 들어 같은 iPhone listing에서 지난번 Balanced Closer, cap $450, opening $390를 저장했다면 다음 진입 때 자동으로 그 값을 채운다. 이후 협상이 cap 안에서 성사되면 해당 후보 strength가 올라가고, 거절되거나 중단되면 낮아져 다음 추천 순위에 반영된다. feedback 저장 결과는 Backend Memory 카드에도 즉시 병합된다. 저장 성공은 초록, 저장 대상이 없으면 노랑, 저장 실패는 빨강으로 보여 디버깅할 수 있게 했다. 추천 점수는 listing 유사도만 보지 않고 card strength와 최근 outcome도 함께 본다. 같은 상품 후보가 둘 이상이면 성공 이력이 있는 후보가 위로 올라가고, 거절/중단된 후보는 같은 조건에서도 자동 적용 임계값을 넘기 어렵게 된다. Term Garden compiler는 iPhone에서 MacBook으로 확장했다. MacBook에서는 battery_cycle_count, keyboard_condition, applecare_status, activation_lock이 협상 전 확인/가격 인하 근거/중단 조건으로 들어간다. 동시에 clean_imei_refused 같은 iPhone 전용 중단 조건은 MacBook draft에 섞이지 않게 분리했다.

5/5 결제 레이어 리뷰 메모: API provider가 HAGGLE_CONDITIONAL_SETTLEMENT_ADDRESS를 읽어 x402 quote metadata에 조건부 정산 주소와 capability를 싣도록 연결했다. 다만 exact x402 결제를 컨트랙트 주소로 직접 보내면 createAndFund()가 호출되지 않아 내부 기록 없이 토큰만 들어갈 수 있으므로, 기본값은 metadata-only로 둔다. 조건부 정산 signer도 추가했다. 이 signer는 approval_policy_hash, agreement_hash, listing_hash, grantNonce를 모두 EIP-712 메시지에 넣어, 사용자가 승인한 조건과 다른 결제/상품/합의로 서명을 재사용하지 못하게 한다. 실제 서버 실행은 HAGGLE_CONDITIONAL_SETTLEMENT_SERVER_EXECUTION=true일 때만 열리며, 다음 단계는 구매자 지갑/facilitator가 contract-call을 만들거나 dedicated receiver/sweep 컨트랙트를 붙이는 것이다.
