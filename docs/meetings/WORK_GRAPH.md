# 주간 작업 그래프 사용법

주간 회의에서 정한 `사람 → 담당 작업 → 단일 리뷰 → 의존 작업`을 한 곳에서 관리한다.
현재 주의 실제 데이터는 [current-week-work-graph.json](./current-week-work-graph.json)이다.
모든 기여자의 시작·구현·리뷰·완료 절차는 [Haggle 개발 참여 규칙](../../CONTRIBUTING.md)을 따른다.

## 내가 할 일 보기

저장소 루트에서 자기 이름이나 별칭을 말한다.

```bash
pnpm work:me -- 정행
pnpm work:me -- Sean
pnpm work:me -- Amy
pnpm work:me -- "나는 정행이야"
```

결과에는 네 영역이 나온다.

1. 이번 주 내가 할 일과 다음 행동
2. 내가 리뷰할 일과 코드보다 먼저 판단할 내용
3. 내 작업을 기다리는 다른 사람의 일
4. 팀이 다음 회의에서 담당자를 정해야 하는 미배정 일

팀 전체는 `pnpm work:me -- --all`로 본다.

## 토요일 회의에서 갱신하는 순서

회의는 보통 20:00 또는 20:30에 시작한다. 정확한 시작 시각과 시간대는 회의 공지에서 확정한다.

1. 지난주 작업의 상태와 증거를 확인한다.
2. 녹음이나 메모에서 새 작업, 담당 후보, 의존성을 추출한다.
3. 본인이 맡겠다고 명확히 확인한 작업만 `ownerId`를 넣는다.
4. 작업마다 담당자와 다른 리뷰어 한 명만 `reviewerId`에 넣고 선택 이유를 기록한다.
   녹음에서 리뷰어까지 합의되지 않았다면 `proposed`, 팀이 확인하면 `confirmed`로 표시한다.
5. 담당자가 불명확한 일은 `unassigned`로 그대로 남긴다.
6. 조회 명령을 실행해 끊긴 연결, 동일 담당자·리뷰어, 리뷰어 누락을 검사한다.
7. 각 담당자가 자기 화면을 읽고 이번 주 분담을 최종 확인한다.

녹음에서 이름이 자주 다르게 들리므로 사람은 안정적인 `id` 하나와 여러 `aliases`를 가진다. 현재 확인된
별칭에는 `성진 = Sean`, `진영 = Amy`가 포함된다.

## 작업 상태

| 상태 | 의미 |
|---|---|
| `planned` | 이번 주에 시작할 예정 |
| `in_progress` | 진행 중 |
| `blocked` | 선행 결정이나 작업을 기다림 |
| `done` | 완료 조건과 증거가 확인됨 |
| `unassigned` | 필요성은 확인됐지만 담당자가 확실하지 않음 |

`unassigned`는 누락이 아니라 의도적인 상태다. 담당자를 추측해 넣는 것보다 다음 회의에서 눈에 띄게
남겨 두는 편이 안전하다.

## 리뷰 요청 설명

리뷰어는 한 명만 지정한다. 담당자는 리뷰를 요청할 때 코드 파일 목록보다 다음 내용을 먼저 전달한다.

- 사용자가 얻게 되는 결과
- 변경 전과 변경 후의 흐름
- 돈, 권한, 데이터, 외부 서비스에서 가장 위험한 실패
- 그 실패를 막거나 발견하는 장치
- 자동 검사, Playwright, staging에서 관찰한 증거
- 리뷰어가 판단해야 할 구체적인 질문

세부 규칙은 [개발 그래프와 리뷰 운영](../mvp/DEVELOPMENT_GRAPH_AND_REVIEW.md)을 따른다.

## 다른 사람에게 작업을 넘길 때

새 담당자는 먼저 자신의 이름으로 그래프를 조회한다. 인계자는 다음 내용을 작업 카드와 그래프에 남긴다.

- 완료된 사용자 결과와 남은 결과
- 현재 상태와 다음 행동
- 실패 재현 방법과 검증 증거
- 선행·후속 작업과 충돌 가능성
- 변경된 담당자와 단일 리뷰어, 변경 이유

기존 담당자를 새 담당자로 바꾸는 것만으로 인계를 끝내지 않는다. 새 담당자와 리뷰어가 확인한 뒤 상태를
갱신하고, 확인되지 않았다면 미배정으로 남긴다.
