## 0. 한 페이지 요약

지난 세션에서 협상엔진과 에이전트 시스템 두 군데를 깊이 파봤음. 결과를 한 줄로 요약하면:

- **협상엔진**: 현 default는 rule-based. LLM은 Decide stage(BARGAINING+COUNTER) 한 군데만 호출. 두 에이전트는 같은 세션 1개를 공유하고 `sender_role`로 토글. HNP는 opt-in wire validation 레이어.
- **에이전트 시스템**: main에 buyer-side intelligence (advisor/preset-tuning/tag-garden/memory) 풍부, seller-side는 거의 빈 상태. 우리가 만들던 8-stat 시스템은 main과 충돌하지 않는 별개 레이어.
- **노트 4개 컨셉 매핑**: 0개가 main에 완전 구현. 1.5개는 인접 시스템 차용 가능, 2.5개는 우리가 채워야 함.
- **결정한 방향**: 카테고리별 term은 **폼으로 수집**, 가중치는 **LLM 대화로 추론**. 프리셋은 카테고리 무관 — 유니버셜 weight 수치만 차별화.
- **당장 할 일**: Agent 스키마 확정 → 카테고리 폼 → LLM 가중치 추론 endpoint → UX 통합 → 검증. 1.5~2주 sprint.

## 1. 배경 — 현 상태 요약

### 1.1 협상엔진의 진실 (v2 trace 기반)

**기본 모드:** Rule-based.

```
NEGOTIATION_ENGINE 환경변수
├─ 'rule' (default, .env.example에도 명시)
│   → executeNegotiationRound() — 순수 규칙 기반
└─ 'llm' (opt-in)
    └─ NEGOTIATION_PIPELINE
        ├─ 'staged' — 6-stage pipeline
        └─ 'legacy' — Step 56 RefereeService (deprecated 추정)
```

**LLM이 실제 호출되는 곳:**

| Stage | 현재 구현 | LLM? |
|---|---|---|
| 1. UNDERSTAND | 정규식 + keyword | ❌ |
| 2. CONTEXT | 코드 조립 | ❌ |
| 3. DECIDE | Skill + LLM 하이브리드 | ✅ (BARGAINING+COUNTER만) |
| 4. VALIDATE | Referee 룰 | ❌ |
| 5. RESPOND | 템플릿 (`// Future: LLM` 주석) | ❌ |
| 6. PERSIST | DB 저장 | ❌ |

→ **LLM은 6 stage 중 1개만**. 나머지는 rule/template.

**두 에이전트 메시지 교환:**

- 같은 `negotiation_sessions` row 1개 공유
- `negotiation_rounds.sender_role`로 누가 보냈는지 구분
- 동기 실행: 한쪽이 POST → 즉시 상대 입장에서 응답 계산
- 비동기 큐/cron 없음

**HNP 프로토콜:**

- Wire-level 검증 (외부 agent 서명, sequence ordering)
- Opt-in: `protocol` 필드 없으면 통과
- 협상 결정 로직과 분리

**3대 정보 누수 지점:**

1. **Stage 1 UNDERSTAND** — 자유 텍스트 nuance가 정규식에서 죽음
2. **Stage 5 RESPOND** — agent 페르소나/stat이 자연어로 못 살아남음
3. **Stage 9 신호 추출** — 라운드 후 학습이 정규식 기반

### 1.2 에이전트 시스템의 진실

**main에 이미 있는 것 (buyer-side intelligence):**

## 2. 결정한 방향

### 2.1 데이터 수집 분리

**카테고리별 term → 폼으로 수집**

- main의 `tag-garden-requirements` 패턴 차용 (이미 80% 있음)
- iPhone slot 정의 → MacBook, vehicles 등 추가
- BUYER 한정 → SELLER도 폼 사용 가능하게 분기

**가중치(weights) → LLM 대화로 추론**

- 사용자가 "가격을 좀 더 중시", "오래 걸려도 괜찮아" 같은 자연어 발언
- LLM이 듣고 `{w_p, w_t, w_r, w_s}` + alpha, beta 추정
- 프롬프트는 일단 거칠게 시작 → 데이터 쌓이면 개선

### 2.2 프리셋의 본질

> **카테고리별로 달라지는 건 프리셋으로 못 함.** 유니버셜 weight 수치만 다른 4개(또는 3개) 프리셋.

- 프리셋 = (universal weights) + (curve params)
- 카테고리별 답변 = 폼이 채움 (프리셋과 무관)
- 사용자별 미세 조정 = LLM 대화가 채움

### 2.3 새 시스템 그림

```
[에이전트 생성]
  ├─ 폼: 카테고리별 term 답변 (예: iPhone → 배터리 90%↑)
  ├─ LLM 대화: 협상 스타일 → weights 추론
  ├─ (옵션) 프리셋 선택: weights 빠른 시작점
  └─ 저장: agent { weights, categoryAnswers, voiceId? }

[협상 시작]
  agent.weights → strategy_snapshot → 라운드 실행
  (current pipeline 그대로 활용)
```

### 3.2 후보 4개

| 프리셋 | 한 줄 | w_p | w_t | w_r | w_s | beta | alpha |
|---|---|---|---|---|---|---|---|
| 🎯 **Bargain Hunter** | 시간 들여도 좋은 가격 | **0.50** | 0.15 | 0.20 | 0.15 | 0.4 (천천히) | 0.5 (압력 약) |
| ⚡ **Quick Closer** | 가격 양보해서 빨리 끝냄 | 0.20 | **0.50** | 0.15 | 0.15 | 2.0 (빨리) | 2.0 (압력 강) |

### 3.3 차별화 sanity test

같은 상황($1000 listing, 24h deadline) 4개 프리셋 적용 시 예상:

| 프리셋 | 합의가 | 라운드 수 | 거절율 |
|---|---|---|---|
| Hunter | $830-880 | 6-10 | 높음 |
| Closer | $920-970 | 2-4 | 매우 낮음 |
| Verifier | $880 또는 walk | 3-7 | 중간-높음 |
| Balancer | $880-920 | 4-6 | 중간 |

수치가 명백히 달라야 = "디테일한 수정 → 디테일한 결과" 원칙 충족.
