# Dispute Module Boundary Design

## Design

Haggle disputes should work in two modes:

- **Native mode:** Haggle commerce orders, payments, shipments, trust scores, and reviewer pools are all internal.
- **Module mode:** an external marketplace sends a trusted transaction snapshot, uses Haggle for dispute resolution, and receives signed settlement instructions or webhooks back.

The product principle is the same in both modes: the client never decides role, cost, tier, or outcome. In module mode, those facts come from a trusted host-platform integration instead of Haggle's own commerce DB.

## Trust Boundary

Untrusted:

- Browser clients.
- User-submitted role fields.
- User-submitted transaction amount, currency, order status, or counterparty IDs.
- External file URLs.

Trusted:

- Haggle internal DB records.
- External platform server-to-server signed transaction snapshots.
- Haggle-controlled evidence storage and upload intents.
- Reviewer/vote aggregation and settlement finalization generated by the dispute service.

## Module Case Model

The external platform supplies a `ModuleTransactionSnapshot`:

```ts
{
  platform_id: "swappa",
  external_order_id: "order_123",
  buyer_actor_id: "buyer_1",
  seller_actor_id: "seller_1",
  amount_minor: 45000,
  currency: "USD",
  status: "DELIVERED"
}
```

The caller supplies only the action:

```ts
{
  requester_actor_id: "buyer_1",
  reason_code: "ITEM_NOT_AS_DESCRIBED",
  summary: "Battery health was misstated.",
  client_request_id: "retry-key"
}
```

The module derives `opened_by` from the transaction snapshot.

## Configuration

Each platform can override dispute economics and reviewer policy:

- tier cost rates and minimums
- platform/reviewer revenue split
- allowed open states
- reviewer counts and shared-pool mode
- AI plaintiff/defendant/expert settings

Defaults must match Haggle native policy so native mode is just the default module configuration.

## AI Review Harness

Haggle dispute AI is platform decision support, not legal advice or a legal decision maker. Product and API names must avoid legal-profession or court-role labels such as lawyer, attorney, counsel, judge, or arbiter.

Approved role names:

- `Case Guide`: party-specific evidence and claim organization for buyers or sellers.
- `Resolution Assessor`: neutral Tier 1 platform review recommendation.

Korean UI can render these as `케이스 가이드` and `1차 검토관`. Avoid `판사`, `변호사`, `중재인`, or names that imply legal authority.

The first implementation boundary lives in `@haggle/dispute-core` as a provider-neutral harness:

- trusted case facts and untrusted party/evidence data are separated into explicit context blocks;
- party statements and evidence text are always treated as untrusted data, not instructions;
- prompts include few-shot examples for condition mismatch, delivery conflict, insufficient evidence, and escalation behavior;
- output is constrained by structured schemas for `dispute_ai_case_guide_v1` and `dispute_ai_resolution_assessor_v1`;
- validation rejects unsupported evidence references, low-confidence non-escalations, prompt-injection non-escalations, invalid score ranges, and refund amounts above platform cap.

The `Resolution Assessor` output is not self-executing. Server code must validate the schema, apply confidence thresholds, enforce refund caps, and escalate to Tier 2 when evidence is insufficient, risk flags are present, high-value policy applies, or the output fails validation.

The API execution boundary lives in `apps/api/src/services/dispute-ai.service.ts`:

- provider adapters implement a small `DisputeAiProvider.completeJson` interface;
- `runCaseGuide` and `runResolutionAssessor` always build prompts through `@haggle/dispute-core`;
- model output is parsed as JSON and then revalidated by the core validators before callers can use it;
- malformed JSON, provider failures, role/party mismatches, unsupported evidence references, and refund-cap violations return typed failures rather than usable recommendations;
- failure results do not include raw model output, prompts, or evidence bodies;
- the xAI adapter is optional and can be swapped without changing the dispute AI contract.

Model policy:

- `Resolution Assessor` should use a stronger reasoning model than the low-latency guide path. xAI currently recommends `grok-4.3` for Chat API use, so the API default is `DISPUTE_AI_RESOLUTION_ASSESSOR_MODEL ?? DISPUTE_AI_MODEL ?? "grok-4.3"`.
- `Case Guide` can default to the faster path: `DISPUTE_AI_CASE_GUIDE_MODEL ?? DISPUTE_AI_MODEL ?? XAI_MODEL ?? "grok-4-fast"`.
- Operators can pin exact model ids by role without changing prompt or validation code.

Cost tracking:

- dispute AI provider responses include token usage and a USD cost estimate when pricing is known;
- `withLLMTelemetry` emits `costUsd` and `costMinorUsd` in structured logs and persists `cost_minor` in DB telemetry mode;
- pricing is resolved from model-specific env overrides first, then global overrides, then built-in defaults for known xAI models;
- supported overrides are `LLM_PRICE_<MODEL>_INPUT_PER_1M_USD`, `LLM_PRICE_<MODEL>_OUTPUT_PER_1M_USD`, `LLM_PRICE_INPUT_PER_1M_USD`, and `LLM_PRICE_OUTPUT_PER_1M_USD`;
- built-in prices are estimates and must be updated or overridden when provider pricing changes.

Video evidence:

- uploaded video remains the source evidence and must not be replaced by derived frames;
- the API can derive `video_keyframe` artifacts with source evidence id, local path, offset seconds, and sample index;
- default extraction is dense enough for short dispute clips: one frame per second, capped at 24 frames;
- high-value disputes raise the default cap to 48 frames;
- operators can tune `DISPUTE_VIDEO_KEYFRAME_INTERVAL_SEC`, `DISPUTE_VIDEO_KEYFRAME_MAX_FRAMES`, `DISPUTE_VIDEO_KEYFRAME_SCALE_WIDTH`, and `DISPUTE_VIDEO_KEYFRAME_JPEG_QUALITY`;
- the hard cap is 96 frames per video so hostile uploads cannot create unbounded storage, compute, or AI context cost;
- when a video is longer than the dense sampling cap, frames are selected across the full duration instead of only from the beginning;
- AI context receives derived artifacts under each evidence item, while future OCR/transcript artifacts can use the same untrusted evidence channel.

## Tier 2/3 Panel Review

Tier 2 and Tier 3 use the same module boundary as Tier 1: clients can request escalation, but they cannot choose economics, reviewer count, reviewer identity, vote weight, or final outcome.

Core invariants:

- Tier 2 costs `max(amount * 2%, $12)` and Tier 3 costs `max(amount * 5%, $30)` unless a platform-specific server config overrides those values.
- Seller deposit requirements are server-computed for Tier 2/3; client-supplied amounts are ignored.
- Reviewer count is derived from transaction amount and tier.
- A panel cannot be tallied until the required number of reviewers has been assigned.
- A panel cannot be tallied while any assigned reviewer vote is pending.
- Votes are aggregated in `@haggle/dispute-core`, not in route code, so the same engine can run inside Haggle native mode or a standalone dispute module service.
- The API finalizer remains responsible for money movement, deposit resolution, webhook emission, and reviewer accounting after the core engine returns a panel decision.

Module escalation endpoints:

`POST /modules/disputes/v1/cases/:id/escalations/preview`

`POST /modules/disputes/v1/cases/:id/escalations`

`POST /modules/disputes/v1/cases/:id/status`

These endpoints use the same HMAC module headers as case preview/create. The escalation request body contains only the external order id, requester actor id, optional target tier, optional reason, and optional client request id. The API loads the original trusted transaction snapshot from dispute metadata, verifies the signed platform owns the case, verifies the requester actor is the buyer or seller in the snapshot, and only allows one-tier advancement.

The response includes the computed next tier cost and seller deposit requirement. The create endpoint persists `tier`, `current_tier_cost`, `current_seller_deposit_requirement`, and append-only escalation history in dispute metadata, then writes a `dispute.case.escalated` webhook outbox row in the same persistence step. Escalation webhook ids include the target tier as a dedupe key so T2 and T3 events for the same dispute do not collide.

When a module dispute reaches a final resolution, Haggle does not execute native refunds or order release against its own commerce tables. Instead, the finalizer persists the resolution and writes a `dispute.settlement.instruction` outbox row in the same persistence step. The instruction includes the final outcome, target action (`refund_buyer` or `release_to_seller`), amount, and currency derived from the trusted transaction snapshot. The external platform remains responsible for applying that instruction in its payment and order system.

## First Code Boundary

This slice adds pure `@haggle/dispute-core` helpers:

- normalize and validate `DisputeModuleConfig`
- compute configurable tier cost
- validate an external open-dispute request against a trusted transaction snapshot
- build and validate provider-neutral dispute AI prompts and outputs
- evaluate Tier 2/3 panel readiness, vote aggregation, outcome mapping, and reviewer reward allocation

No DB or HTTP code belongs in this boundary.

## Server-to-Server API Boundary

External platforms must call Haggle through a server-to-server namespace:

`POST /modules/disputes/v1/cases/preview`

This endpoint does not create a case yet. It authenticates the platform request, validates the transaction snapshot against module policy, derives `opened_by`, and returns dispute cost previews. It exists so integrators can validate their integration before write paths are enabled.

### Required Headers

- `x-haggle-module-platform-id`
- `x-haggle-module-timestamp`
- `x-haggle-module-signature`
- `x-haggle-idempotency-key`

### Signature

The signature is HMAC-SHA256 over:

```text
<timestamp>.<method>.<path>.<sha256(rawBody)>
```

The header format is:

```text
sha256=<hex hmac>
```

The timestamp has a five-minute tolerance. Future write endpoints will persist the idempotency key; preview requires it now so all module clients start with the correct contract.

### Platform Configuration

Module economics are not accepted from the request body. They are resolved from Haggle-side platform configuration, currently:

`DISPUTE_MODULE_PLATFORM_SECRETS`

Legacy single-secret format remains valid:

```json
{
  "platform_1": "platform-api-secret-with-length"
}
```

For production rotation, each platform can provide the active secret and temporary previous secrets:

```json
{
  "platform_1": {
    "current": "new-platform-api-secret-with-length",
    "previous": ["old-platform-api-secret-with-length"]
  }
}
```

The verifier accepts any configured valid secret for that platform during the rotation window. New SDK clients should sign with `current`; `previous` exists only to keep in-flight jobs and retry queues working until the old secret can be removed.

`DISPUTE_MODULE_PLATFORM_CONFIGS`

```json
{
  "platform_1": {
    "tier2_rate": 0.008,
    "tier2_min_cents": 5000,
    "reviewer_share": 0.6,
    "platform_share": 0.4
  }
}
```

This keeps tier cost, reviewer share, shared pool usage, and AI settings out of client control.

Invalid server-side platform configuration is a hard error. The API must not silently fall back to default economics when a configured platform has malformed rates, invalid shares, or an invalid status policy.

## Module Case Creation

The write path is:

`POST /modules/disputes/v1/cases`

It uses the same signed request body as preview, but persists a case. The platform still sends a trusted transaction snapshot and a requested open action; Haggle derives the party role, cost preview, and internal case state.

### Persistence Strategy

Module mode should be able to run as a separate service without depending on Haggle commerce orders. For this slice, the API maps:

```text
platform_id + external_order_id -> deterministic internal order UUID
```

That lets the existing `dispute_cases.order_id` column and active-dispute unique index protect one active dispute per platform transaction. The external identifiers and transaction snapshot are stored in dispute metadata so the module can later emit webhooks or settlement instructions back to the platform.

### Idempotency

`x-haggle-idempotency-key` is persisted in case metadata for create requests. If the same platform transaction already has an active dispute:

- the same idempotency key returns the existing dispute as an idempotent replay;
- a different idempotency key is rejected with `ACTIVE_MODULE_DISPUTE_EXISTS`.

The route also handles unique-index races by re-reading the active case and applying the same idempotency check.

The idempotency key is scoped to `platform_id` and bound to a canonical request fingerprint. Reusing the same key with a different request body is rejected with `IDEMPOTENCY_KEY_REUSED`, even if the external order id is different. This prevents accidental or malicious key reuse from creating unrelated cases under one retry key.

Create replay checks run before current platform configuration validation. Once a case has been created, retrying the same request should return the original case even if a later configuration deploy is temporarily invalid.

The write transaction persists both the dispute case and a `dispute_module_idempotency_keys` record. Unique constraints protect:

- one idempotency key per platform;
- one active dispute per platform transaction through the deterministic internal order id.

### Stored Metadata

Created module cases store:

- `source = "dispute_module_api"`
- `module_version`
- `platform_id`
- `external_order_id`
- `requester_actor_id`
- `opened_by_actor_id`
- `client_request_id`
- `idempotency_key`
- `transaction_snapshot`
- computed costs
- server-resolved config summary

## Signed Platform Webhooks

Module mode needs a reliable output path back to external platforms. This slice adds the first API-side primitive:

- `dispute.case.created` envelope generation after successful module case creation
- platform-specific webhook config from `DISPUTE_MODULE_PLATFORM_WEBHOOKS`
- HMAC-SHA256 signature over:

```text
<timestamp>.<eventId>.<sha256(rawBody)>
```

Headers:

- `x-haggle-webhook-id`
- `x-haggle-webhook-timestamp`
- `x-haggle-webhook-signature`

Example config:

```json
{
  "platform_1": {
    "url": "https://platform.example/webhooks/haggle/disputes",
    "secret": "platform-webhook-secret-with-length",
    "allow_private_network": false
  }
}
```

Outbound webhook URLs must be HTTPS, must not include credentials, and must not target localhost, link-local, private, carrier-grade NAT, benchmark, multicast, or reserved IP ranges by default. `allow_insecure_http` and `allow_private_network` are development or tightly controlled deployment overrides, not normal production settings.

Webhook durability now uses `dispute_module_webhook_outbox`. On module case creation, the API writes the dispute case, module idempotency key, and `dispute.case.created` outbox row in the same transaction when the database adapter supports transactions. Delivery runs only after that persist step succeeds, and delivery state is tracked as:

- `PENDING`: event is persisted and eligible for first delivery.
- `PROCESSING`: dispatcher claimed the row and set a short lease in `next_attempt_at`.
- `DELIVERED`: platform endpoint returned a successful HTTP status.
- `FAILED`: latest attempt failed, with `attempt_count`, `last_error`, and `next_attempt_at` recorded for retry scheduling.
- `DEAD_LETTER`: retry budget is exhausted and automatic delivery is paused.

The API cron runner includes a `dispute-module-webhook-outbox` dispatcher when `ENABLE_CRON=true`. It claims due `PENDING`/`FAILED`/expired `PROCESSING` rows using `FOR UPDATE SKIP LOCKED`, delivers them with the same signature contract, and records success or retry metadata. This keeps platform output recoverable if the API process exits between case creation and webhook delivery.

Retry budget defaults to 10 attempts and can be tuned with `DISPUTE_MODULE_WEBHOOK_MAX_ATTEMPTS`. The dispatcher result includes a `deadLettered` count and minimal event references, and the cron job logs any batch that creates a dead-letter row at error level. If `DISPUTE_MODULE_WEBHOOK_DEAD_LETTER_ALERT_URL` is configured, the cron job also POSTs a signed optional ops alert with summary counts and event/platform/dispute ids only. It does not include webhook payload bodies, signatures, secrets, transaction snapshots, or evidence.

Alert config:

```json
{
  "DISPUTE_MODULE_WEBHOOK_DEAD_LETTER_ALERT_URL": "https://ops.example/alerts",
  "DISPUTE_MODULE_WEBHOOK_DEAD_LETTER_ALERT_SECRET": "ops-alert-secret-with-length",
  "DISPUTE_MODULE_WEBHOOK_DEAD_LETTER_ALERT_ALLOW_PRIVATE_NETWORK": "false"
}
```

Operators can inspect stopped rows through `GET /admin/dispute-module-webhooks/dead-letter` and reset a failed/dead-letter event through `POST /admin/actions/dispute-module-webhook-replay` with an `eventId` and replay `reason`; replay resets the row to `PENDING`, clears the last error, starts a fresh attempt count, and records the reason in the admin audit log.

The remaining production work is richer bulk replay controls and provider-specific alert adapters.
