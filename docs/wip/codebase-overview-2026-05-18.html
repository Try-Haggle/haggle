① 웹 진입 — 셀러 시나리오

  1. 마케팅 페이지 도착 → 가입 (/sign-up, Supabase Auth)
  2. /sell/listings/new에서 listing draft 작성
  3. 셀러 에이전트(preset) 선택 또는 /sell/agents/new에서 커스텀 생성
  4. publish → 공개 링크 /l/[publicId] 발급
  5. 구매자가 협상 들어오면 /sell/dashboard에 알림, /sell/negotiations/[sessionId]에서 실시간 관찰

② 웹 진입 — 바이어 시나리오

  1. 공유 링크 /l/[publicId] 클릭 (로그인 없이 접근)
  2. buyer-landing.tsx에서 매물 + 셀러 에이전트 확인
  3. strategy-chat.tsx에서 자신의 협상 전략(예산/스타일) 채팅으로 설정
  4. 세션 시작 → /buy/negotiations/[sessionId]로 리다이렉트
  5. 플레이백 아레나에서 협상 진행 + 결제 단계

③ MCP 진입 — 외부 AI가 우리 서비스를 도구로 사용

Claude 등 MCP 클라이언트가 POST /mcp로 붙어서, 우리가 노출한 도구를 호출한다. 로직은 REST 라우트와 같은 서비스 레이어를 공유 — 별도 구현 없음.

주요 도구 (apps/api/src/mcp/tools/index.ts):

  • haggle_start_draft · haggle_apply_patch · haggle_publish_draft — 리스팅 생성
  • haggle_create_session · haggle_submit_offer — 협상 시작/오퍼 제출
  • 전략·에이전트 선택 도구들

즉, MCP는 "AI를 위한 우리 웹의 미러" 역할. 같은 일을 도구 호출로 한다.

엔진 실행기 (Executor Factory)

lib/executor-factory.ts가 env 변수로 세 모드 중 하나를 고른다:

  • rule — engine-session의 executeRound() (순수 룰)
  • llm + legacy — 구버전 LLM 실행기
  • llm + staged default — 6단계 파이프라인 (현재 메인)

셋이 같은 인터페이스를 구현하지만 내부는 완전히 다른 코드. fallback 없음.

4. 협상 엔진 — 6단계 파이프라인

현재 메인 경로. apps/api/src/negotiation/pipeline/executor.ts → pipeline.ts가 한 라운드를 6단계로 처리한다. LLM은 단 한 군데(Stage 3 Decide)에서만 호출된다.

1. UNDERSTAND들어온 메시지 파싱
no LLM
2. CONTEXTBriefing · coaching · skill stack 조립
3. DECIDELLM 호출
Grok Fast
→ ProtocolDecision
4. VALIDATE가드 검사
수학·프로토콜
5. RESPOND유저용 메시지 렌더
6. PERSISTround + memo 저장
phase 전이

한 라운드의 풀 호출 체인

HTTP POST /negotiations/sessions/:id/offers
  └─ routes/negotiations.ts
     └─ getExecutor()  (executor-factory.ts)
        └─ executeStagedNegotiationRound()
           ├─ memory-reconstructor.ts  ← DB의 이전 rounds에서 CoreMemory 복원
           ├─ pipeline.ts (6 stages)
           │   └─ adapters/xai-client.ts  ← LLM 호출
           ├─ referee/validator.ts        ← 가드
           ├─ rendering/                  ← 유저 메시지 생성
           └─ phase/phase-machine.ts      ← 단계 전이 + DB 쓰기

엔진 패키지와의 관계

  • @haggle/engine-session — 라운드 실행, 전략 스냅샷, HNP 타입. Stage 6의 phase 전이와 룰 모드에서 사용.
  • @haggle/engine-core — 효용 계산, Faratin 양보 곡선, 카운터 오퍼 산출. 주로 coach(레퍼리)와 스킬 모듈이 사용.

중요한 디테일: LLM Stage 3는 engine-core의 효용 수식을 직접 쓰지 않는다. LLM이 자유롭게 결정을 내리고, 효용은 사후 로깅용으로만 계산된다. → 5번 섹션의 "끊긴 곳" 참고.

현재 끊긴/모호한 부분

⚠ 페르소나가 세션에 묶여있지 않다.

세션 생성(createSession) 시점에 buyer_agent_id / seller_agent_id를 저장하지 않는다. 데모 라우트에서만 오퍼 페이로드로 매번 넘긴다. 즉, 같은 세션에서 라운드마다 페르소나가 바뀔 수도 있다(검증 없음).

고민할 점: 페르소나를 세션에 anchor할지, listing에 anchor할지, preset에 anchor할지 결정 필요.

⚠ LLM이 엔진 수식을 안 본다.

Stage 3는 자유 LLM 결정. engine-core의 computeUtility, computeCounterOffer는 레퍼리(coach)와 일부 스킬 모듈에서만 사용. 코어 결정이 수학적으로 일관되지 않을 수 있다.

고민할 점: Stage 4(Validate)에서 utility 기준 가드를 더 강하게 걸지, Stage 3 프롬프트에 수치를 더 넣을지.

✗ HNP 경로가 별도다.

routes/negotiations.ts 안에 HNP 오퍼 제출용 별도 코드 패스가 있고, 이건 6단계 파이프라인을 통과하지 않고 createHnpTransactionHandoff()를 직접 부른다. 두 경로 사이에 상태가 어긋날 위험.

⚠ Rule / LLM fallback 없음.

NEGOTIATION_ENGINE=llm인데 xAI가 죽으면 룰 모드로 떨어지지 않는다. 라운드 실패 처리만 됨.

7. 태그 시스템 — 케이스 스터디 (반쯤만 연결된 정원)

이전 섹션 DB 표에서 한 줄로만 적어둔 tags / tag_graph / tag_idf_cache는 실제로는 가장 큰 "끊긴 곳"의 대표 사례라서 따로 펼친다. 한 줄 요약: 레일은 다 깔려있는데 종착역이 없다. 태그를 모아두는 정원은 작동하지만, 그 정원을 실제로 쓰는 소비자가 거의 없다.

1) 스키마 — 무엇이 저장되나

테이블역할활성도
tags 마스터 태그 (name, normalizedName, status, category, useCount, idf, aliases) 활성
tag_graph / tagEdges 부모↔자식 DAG 엣지 (다중 부모 지원). 레거시 단일 parentId 대체용 seed만, 런타임 쓰기 없음
tag_idf_cache TF-IDF 캐시 (tag → docCount, idfScore, totalDocs) 기동 시 로드, 갱신 잡 없음
tagSuggestions LLM이 못 찾아서 누락된 태그 후보 (PENDING → APPROVED/REJECTED/MERGED) 활성
tagPlacementCache LLM 태그 배치 결과 캐시 (sha256 key) 활성
expertTags 유저별 도메인 전문성 (별도 시스템, 태그에서 자동 산출 안 됨) 수동 qualify

2) 어디에 들어가는가 — 리스팅 publish 흐름의 한 단계

셀러는 태그를 직접 고르지 않는다 (웹 UI에 태그 피커 없음). draft를 publish할 때 서버가 자동으로 붙인다.

셀러: publish
/sell/listings/new
→
draft.service.ts
→
placeListingTags()
tag-placement.service.ts
→
tags +
tagPlacementCache +
tagSuggestions

L0 ~ L8 다단계 파이프라인

L0  cache lookup        sha256(title|desc|category|candidates) → tagPlacementCache
L1  candidate gather    임베딩 기반 유사 listing 의 태그
L2  global top-N        IDF 상위 + 타이틀 n-gram 매치
L3  filter              ancestor pruning + 낮은 IDF 컷
L5  LLM rank            gpt-4o-mini 가 후보 중에서 "선택" (추출 아님)
L8  persist             tagPlacementCache 저장 + 누락분은 tagSuggestions PENDING

중요: LLM은 설명에서 새 태그를 추출하지 않는다. 미리 만들어진 후보 풀에서 고른다. LLM이 "이건 후보에 없는데 필요해 보임"이라고 표시한 것만 tagSuggestions로 관리자 큐에 들어간다.

3) 어떻게 저장되는가

  • listing_drafts.tags — text array, 선택된 태그명 직접 저장
  • listings_published.snapshotJson — publish 시점 스냅샷
  • tags — 전역 마스터 (useCount, idf 누적)
  • tagSuggestions — 관리자가 승인하면 새 tags row 생성 (status=CANDIDATE)
  • tag_graph — 현재 런타임 쓰기 코드 없음. seed 데이터만 존재.

6) 그런데 — 정원의 소비자가 거의 없다

✗ 협상 엔진이 태그를 안 본다.

engine은 strategySnapshot의 p_target / p_limit / max_rounds / category / item_model만 본다. "luxury" 태그가 있으면 프리미엄 전략, "vintage"면 다른 어휘 — 그런 분기가 전혀 없다.

✗ 바이어 검색/브라우즈에서 태그 안 쓴다.

/browse 페이지에 태그 필터 없음. 카테고리·컨디션·가격으로만 필터. 태그가 snapshotJson 안에 묻혀있을 뿐.

⚠ tag_graph (DAG)가 사실상 dead.

스키마와 seed는 있는데 런타임에 쓰는 코드가 없다. L3의 "ancestor pruning"이 이 그래프를 읽기로 되어있지만 현재는 placeholder. 부모-자식 관계를 진짜로 활용하려면 별도 작업 필요.

⚠ tag_idf_cache 갱신 잡 없음.

기동 시 메모리로 로드만 함. listing이 많이 추가되어도 IDF가 자동으로 다시 계산되지 않는다. 점점 stale해진다.

⚠ expertise_badges 가 태그에서 자동 산출 안 됨.

expertTags 테이블이 따로 있고, /tags/:tagId/experts/qualify로 수동 부여. 분쟁 결과·거래 이력에서 자동으로 끌어오는 로직 없음.

⚠ term_intelligence_terms 와 태그 시스템이 분리되어있다.

둘 다 OBSERVED/CANDIDATE → ... → OFFICIAL → DEPRECATED 비슷한 라이프사이클을 갖지만 서로 다른 테이블, 다른 목적 (term-intelligence는 대화에서 일반 용어 추출). 통합 또는 명시적 분리가 필요.

7) 한 줄 진단

✅ 입력 측 (listing → tag placement → 캐시·승인 큐 → 관리자 garden) 은 완전히 연결되어있다.
❌ 출력 측 (검색·전략·추천·전문성) 은 거의 비어있다.

= 데이터는 모이는데 안 쓰는 상태. 정리할 때 결정해야 할 것:

  1. 이 정원을 실제로 쓸 곳을 하나만 정해서 연결한다 (예: 검색 필터 또는 전략 어휘 가중치). 그러면 나머지가 자동으로 가치를 갖는다.
  2. 아니면 tag_graph / tag_idf_cache 같은 dead 부품을 잠깐 archive하고 핵심 태그 + 승인 큐만 남긴다. 나중에 필요할 때 다시 부활.

7) 협상엔진 + 에이전트 시스템과의 연결

✓ 잘 연결되어있음.

협상 라운드가 NEAR_DEAL 상태에 도달하거나 바이어가 수락 버튼을 누르면, routes/negotiations.ts가 bus.publish()를 호출해 즉시 알림이 흐른다. payload는 라이브 세션 상태에서 스냅샷 (listing title, agreed price, buyer/seller name).

⚠ 단방향이다 (one-way push).

알림은 협상 결과를 유저에게 알리는 쪽으로만 흐른다. 알림 클릭/읽음 이벤트가 협상 엔진 쪽으로 다시 피드백되지는 않음. (현재로선 필요하지도 않아 보임 — 메모하는 수준.)

⚠ 협상 이벤트 2개만 wire되어있음.

현재 wire된 협상 이벤트는 session.concluded + offer.accepted 두 개뿐. 다른 단계(분쟁 발생, 배송 시작, 페이먼트 정산 등)는 카탈로그 확장 + 이벤트 발행 추가가 필요.
