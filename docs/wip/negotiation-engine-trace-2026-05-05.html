0. 한 페이지 요약 (정정)

  1. 현재 production default = Rule-based. NEGOTIATION_ENGINE env가 명시되지 않으면 'rule'이 기본값. 사용자가 협상 버튼 누르면 executeNegotiationRound() (순수 규칙 기반)이 돈다.
  2. LLM은 opt-in. NEGOTIATION_ENGINE=llm로 켜야 staged pipeline이 도는데, 그것조차도 6 stage 중 1개(Decide)만 진짜 LLM 호출. Understand는 정규식, Respond는 템플릿.
  3. 두 에이전트는 같은 negotiation_sessions 행 1개를 공유. 라운드 자체에 sender_role 컬럼이 있어 누가 보낸 건지 구분. 같은 세션, 라운드별 sender 토글.
  4. HNP는 옵션 wire-level 검증 레이어. 외부 에이전트가 envelope+서명 보내면 검증. 안 보내면 그냥 통과. 협상 결정 로직과 분리.
  5. Demo 라우트(intelligence-demo, negotiation-demo)는 in-memory 시뮬레이션. Production의 DB-backed round persistence와 별개. 주로 LLM stage 품질 검증용.
  6. 사용자가 그린 흐름("agent → LLM 생성 → 다른 agent가 LLM으로 읽음 → 응답")은 절반만 가능. Decide의 LLM 보강은 있지만, Understand의 자유 텍스트 LLM 파싱과 Respond의 LLM 응답 생성은 미구현.

1. 현재 운영 default — Rule-based vs LLM의 실체

1.1 분기점: executor-factory.ts

매 라운드 라우트(negotiations.ts:378)가 getExecutor()를 호출하면 다음 분기:

export function getExecutor(): RoundExecutor {
  const mode = getEngineMode();          // ← NEGOTIATION_ENGINE env 읽음
  if (mode === 'llm') {
    const pipelineMode = getPipelineMode();  // ← NEGOTIATION_PIPELINE env 읽음
    if (pipelineMode === 'staged') {
      return executeStagedNegotiationRound;  // 6-stage pipeline
    }
    return executeLLMNegotiationRound;       // legacy LLM (Step 56 RefereeService)
  }
  return executeRuleBasedRound;          // ← DEFAULT
}

// config.ts:16-20
export function getEngineMode(): NegotiationEngineMode {
  const mode = process.env.NEGOTIATION_ENGINE;
  if (mode === 'llm') return 'llm';
  return 'rule';                         // ← env 명시 없으면 무조건 'rule'
}

2. 두 에이전트가 메시지 주고받는 메커니즘 (사용자가 가장 헷갈려한 부분)

2.1 같은 세션 1개를 공유한다

Buyer agent와 Seller agent는 각자 다른 세션을 열지 않음. 하나의 negotiation_sessions row를 공유하고, 라운드별로 누가 보냈는지 sender_role로 구분:

negotiation_sessions
├── id: UUID                      ← 1개
├── role: 'BUYER' | 'SELLER'      ← 이 세션의 "주인공" 시점
├── buyer_id, seller_id           ← 양쪽 user 다 기록
├── counterparty_id               ← 상대 user
└── strategy_snapshot: jsonb      ← 한쪽의 strategy

negotiation_rounds                ← 같은 session_id 아래 N개
├── round_no: 1, 2, 3, ...
├── sender_role: 'BUYER' | 'SELLER'   ← 이 라운드 보낸 쪽
├── price_minor                       ← 이 라운드의 incoming 가격
├── counter_price_minor               ← 응답 가격
└── decision                          ← 응답 결정

2.2 라운드 흐름 — 예시 트레이스

Buyer가 첫 오퍼($85) 내고, Seller가 응답($87 counter)하는 시나리오:

① Buyer: POST /negotiations/sessions/:id/offers
   body: { sender_role: 'BUYER', price_minor: 8500 }

   서버 동작 (동일 트랜잭션 안에서):
   ├─ SELECT session FOR UPDATE
   ├─ 인바운드로 인식: { sender: BUYER, price: 8500 }
   ├─ Seller의 strategy_snapshot 로드 (같은 row에서)
   ├─ Seller 입장에서 의사결정 (session.role='SELLER' 시점)
   │  → decision='COUNTER', counterPrice=8700
   ├─ INSERT round { sender_role='BUYER', price=8500, counter=8700, decision='COUNTER' }
   └─ COMMIT
   응답: 다음 round 정보 + counter=8700

② Seller: 위 응답 받고 POST /negotiations/sessions/:id/offers
   body: { sender_role: 'SELLER', price_minor: 8700 }

   서버 동작:
   ├─ SELECT session FOR UPDATE
   ├─ 인바운드: { sender: SELLER, price: 8700 }
   ├─ Buyer의 strategy_snapshot 로드
   ├─ Buyer 입장에서 의사결정
   │  → decision='COUNTER' or 'ACCEPT' or ...
   └─ INSERT round { sender_role='SELLER', price=8700, ... }
중요한 포인트:
  • 매 라운드는 한쪽이 직접 API 호출해야 다음으로 진행. 자동 펌프(cron, webhook) 없음.
  • 동기 실행: 라운드 제출 → 즉시 상대 입장에서 응답 계산. 비동기 큐 없음.
  • Strategy는 한 row에 한 개만 저장돼있는 듯. 양쪽 strategy를 어떻게 같은 row에 합쳐 보관하는지는 코드 더 봐야 확실 (mystery).

2.3 한 명만 AI인 경우

한 명이 사람, 한 명이 AI agent인 경우 — 사람의 메시지(가격 + 자유 텍스트)는 같은 POST /offers로 들어감. AI 측 응답은 자동으로 다음 라운드에서 계산. 즉 AI가 자기 차례에 응답을 직접 만드는 건 다음 incoming 라운드를 받을 때 일어남, 별도 cron 아님.

5. 한 라운드 상세 트레이스 (10단계)

아래는 Rule-based 경로 기준. LLM 경로는 Section 6 참고.

Stage 0

트랜잭션 + 행 잠금 DB
BEGIN; SELECT * FROM negotiation_sessions WHERE id=? FOR UPDATE;

Stage 1

재구성 (DB → engine 타입) 순수
reconstructSession(dbSession, dbRounds) → NegotiationSession
reconstructStrategy(strategySnapshot)  → MasterStrategy

Stage 2

Context 조립 순수
assembleContext(strategy, roundData) → NegotiationContext

Stage 3

Utility 계산 순수
computeUtility(ctx) → { u_total, v_p, v_t, v_r, v_s }
LLM 호출 0회. 4D 가중합산.

Stage 4

의사결정 (6-tier 규칙) 순수
makeDecision(utility, thresholds, session_state)
  → ACCEPT | COUNTER | REJECT | NEAR_DEAL | ESCALATE
순수 if/else. LLM 절대 안 씀.

Stage 5

Counter Offer (Faratin) 순수
P(t) = p_start + (p_limit - p_start) × (t/T)^(1/beta)

Stage 6

세션 상태 전환 순수
transition(status, event) → newStatus
rounds_no_concession 카운터 업데이트

Stage 7

메시지 객체 생성 템플릿

Rule-based 경로에서는 구조화된 객체만 생성 — 자연어 텍스트 X. 자연어가 필요하면 LLM 경로의 Stage 5(RESPOND)가 처리.

Stage 8

DB 저장 DB
createRound() + updateSessionState()  -- 낙관적 잠금

Stage 9

신호 추출 + 메모리 기록 정규식 DB

  → recordTermCandidates()             -- term_intelligence_terms
  → recordUserMemoryCards()            -- user_memory_cards
  → insertMarketSignals()              -- market_conversation_signals
현재 LLM 안 씀. 정규식 매칭으로 신호 뽑음 → 미묘함 손실 큼.

Stage 10

COMMIT + Post-commit NET
COMMIT;
broadcastToSession()       // WebSocket
eventDispatcher.dispatch() // negotiation.agreed/terminal/...
executeGroupOrchestration() // if groupId

6. LLM은 정확히 어디서 호출되나 (Stage별 검증)

여기가 v1에서 가장 모호했던 부분. 실제로 LLM 호출되는 곳은 1군데.

6.1 Staged Pipeline 6단계 — LLM 호출 진실

#Stage현재 구현LLM 호출?비고

6. 최종 결정: LLM이 sane하면 LLM, 아니면 skill로 fallback

LLM 입력에 들어가는 정보:

  • Memory boundary (가격 한도, 협상 가능 범위)
  • Session memory (이전 라운드 요약)
  • Coaching context (opponent_pattern, concession_rate)
  • Recent facts (최근 5 라운드)
  • L5 market signals (선택)
  • Memory card brief (user_memory_cards)
  • Evermemo brief (자동 학습 메모리)
빈 곳 1 — Understand에 LLM 없음: 사용자가 "배송이 빠르면 좋겠어요" 같은 자유 텍스트를 보내도 정규식이 "shipping" 같은 keyword만 잡음. 의미/감정/제약을 LLM이 깊게 파싱하지 않음.
빈 곳 2 — Respond에 LLM 없음: 응답 메시지 생성도 템플릿. agent의 voice/stat이 자연어 응답에 정량적으로 반영되지 않음. respond.ts에 // Future: LLM message generation 주석만 있고 fallback이 template로 즉시 떨어짐.

9. HNP 프로토콜의 실 역할 (정정)

v1에서 모호했던 HNP 명확하게:

9.1 HNP는 무엇인가

  • Wire-level 검증 레이어. 외부 에이전트 서버(다른 머신/시스템)가 envelope+서명 보낼 때 진위/순서 검증.
  • 핵심 시스템과 완전히 분리. 협상 결정 로직은 HNP 없이도 그대로 작동.
  • Opt-in. 라운드 보낼 때 protocol 또는 hnp 필드 없으면 검증 안 함, 그냥 통과.

9.2 HNP가 검증하는 것 (3단계)

// negotiations.ts:367-375 — 라운드 라우트에서 검증
if (normalized.hnp || normalized.protocol) {
  const result = await validateHnpIngress(db, sessionId, { envelope, protocol });
  if (!result.ok) return reply.code(result.status).send(result.body);
}

// hnp-ingress.service.ts:47-108 — 3단계 검증
1. validateHnpDetachedSignature()
   → 외부 agent의 private key 서명을 trusted JWKS로 verify
2. validateHnpEnvelopeConformance()
   → version, capability, issues, settlement preconditions 형식 확인
3. validateHnpProtocolOrder()
   → 같은 세션 내 sequence ordering, duplicate, staleness 확인

9.3 Wire format vs Internal metadata

역할설명
Wire format 외부 agent가 우리 서버로 보낼 때 envelope. 서명 포함. 다른 서버 agent의 진위 보장.
Internal metadata 검증 통과한 envelope이 round.metadata.protocol.hnp에 저장됨. 이후 라운드의 sequence 비교/멱등성에 활용.
사용자 질문 답: "LLM 생성 메시지 + 숫자/정보를 묶어서 다른 쪽으로 보낼 때 HNP 쓰이나?" — Yes, 정확히 그 시점. 외부(또는 분리된) agent 서버가 자기 LLM이 만든 메시지를 envelope으로 감싸서 우리 서버에 POST할 때 진위/순서 검증. 단, 같은 서버 안에서 양쪽 agent가 도는 경우엔 HNP 없이도 작동. 즉 HNP는 "두 시스템이 서로 신뢰할 수 없을 때 켜는 지퍼".

11. 사용자가 그린 흐름 vs 현실의 차이

11.1 사용자가 그린 새 협상 모델

구매자 에이전트 (저장된 정보 → LLM 생성)
    ↓ 메시지 (자연어 + 숫자)
판매자 에이전트가 LLM으로 읽음
    ↓ 판매자 stats 반영 → LLM 응답 생성
구매자 에이전트가 LLM으로 읽음
    ↓ 반복

11.2 코드 단계별 매핑

흐름의 단계현재 코드상태
"저장된 정보 로드" strategy_snapshot + user_memory_cards + evermemo_brief ✅ 가능
"LLM이 메시지 생성" Decide stage에서 BARGAINING+COUNTER 한정 ⚠️ 부분만
"메시지 자연어 텍스트화" Respond stage가 템플릿. // Future: LLM 주석만 ❌ 미구현
"상대 agent가 자유 텍스트 LLM으로 읽음" Understand stage가 정규식 ❌ 미구현
"판매자 stats 반영해 응답" Decide LLM prompt에 voice profile + memory 들어감. Stat은 결정론적 변환만 (engine params) ⚠️ 일부
"라운드 반복" 같은 세션 row + sender_role 토글로 가능 ✅ 가능
"이전 라운드 학습 → 다음에 활용" round_facts + memory cards 저장. 활용은 부분 ⚠️ 부분

11.3 진짜 새 모델 만들려면 채워야 할 것

1. Understand stage에 LLM 활성화. 자유 텍스트 → 의도/감정/제약/태그 추출. 현재 정규식이 잡지 못하는 nuance를 잡아 다음 stage로 넘김. 위치: understand.ts.
2. Respond stage에 LLM 활성화. 결정 + voice + stat + memory → 자연어 응답. 현재 fallback으로 떨어지는 // Future 분기 구현. 위치: respond.ts:21-32.
3. Decide LLM prompt에 stat 정량 주입. 현재는 voice/memory만 들어감. 8-stat 벡터를 prompt에 "anchoring=85, tenacity=70, ..." 같이 넣어 LLM이 정량적으로 행동 조정. 위치: adapter.buildUserPrompt().
4. Stage 9 신호 추출에 LLM 활성화. 현재 정규식이 nuance 죽임. LLM으로 신호 풍부도 ↑ → memory cards quality ↑ → 다음 라운드 fidelity ↑.
5. Production default를 NEGOTIATION_ENGINE=llm로 전환. 위 1-4가 갖춰지면 default를 LLM 경로로. 비용/지연/리스크 trade-off 결정 필요.

12. 최종 종합

현 상태 한 줄: "rule-based 4D utility 엔진이 동작하고, LLM은 Decide의 BARGAINING+COUNTER 한정으로만 곁들여 호출. 양쪽 에이전트는 같은 세션 1개를 공유하며 sender_role로 토글. HNP는 외부 agent 신뢰가 필요한 경우에만 켜지는 옵션 검증 레이어."

사용자가 그린 LLM 중심 새 모델 한 줄: "절반은 코드에 있고, 절반은 // Future 주석으로 비어있음. Understand의 LLM 파싱과 Respond의 LLM 응답 생성이 가장 큰 빈 곳."

정보 fidelity 관점에서 가장 큰 누수 지점 3개:

  1. Stage 1 UNDERSTAND — 자유 텍스트의 nuance가 정규식으로 죽음
  2. Stage 5 RESPOND — agent 페르소나/stat이 자연어로 못 살아남음 (템플릿)
  3. Stage 9 신호 추출 — 라운드 후 학습이 정규식 기반이라 약함
