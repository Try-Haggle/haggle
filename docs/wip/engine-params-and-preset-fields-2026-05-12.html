1. 협상 엔진이 요구하는 17 fields

협상 엔진(@haggle/engine-core)이 한 라운드를 실행하려면 17개 파라미터 전부가 값이 있어야 굴러간다. 이걸 EngineParameters라고 부른다.

17개를 의미에 따라 묶으면 5가지 그룹:

Group 1 — Weights (4) 합 = 1.0

  • w_p (price)
  • w_t (time)
  • w_r (risk)
  • w_s (social)

Group 2 — Behavior curves (4)

  • alpha (시간 압력 곡선)
  • beta (양보 속도, Faratin)
  • u_threshold (walk-away 경계)
  • u_aspiration (만족 utility)

Group 3 — Sub-params attached to weight dimensions (9)

  • anchor_ratio  price
  • v_t_floor  time
  • w_rep  risk
  • w_info  risk
  • r_score_minimum  risk
  • i_completeness_minimum  risk
  • v_s_base  social
  • n_threshold  social
  • late_round_aggression_modifier  social

Group 4 — Market awareness (3)

  • gamma
  • market_utilization
  • cross_pressure_sensitivity

4 + 4 + 9 + 3 = 20개로 보이지만 — w_info는 사실 1 − w_rep로 자동 계산되는 derived 값이라 독립 필드 17개. 그래서 "엔진이 요구하는 17 fields".

3. 옵션 C 구분 — 프리셋별 / 공통 / 파생

옵션 C는 "의미 있는 sub-param까지 프리셋이 직접 결정, market 3개만 공통 NEUTRAL"이다.

처지몇 개포함 필드
프리셋별 명시 13 w_p, w_t, w_r, w_s  ·  alpha, beta, u_threshold, u_aspiration  ·  anchor_ratio, v_t_floor  ·  w_rep, r_score_minimum, i_completeness_minimum, v_s_base, n_threshold, late_round_aggression_modifier
(weights 4 + curves 4 + sub-params 8 = 16, 단 w_info는 derived 제외)
모든 프리셋 공통 3 gamma, market_utilization, cross_pressure_sensitivity — market 차원은 별도 axis라 프리셋 차별화 효과 약함. LLM tuning이 나중에 채울 자리.
파생 1 w_info = 1 − w_rep

잠시: 위에서 "프리셋별 명시 13"이라고 했는데 셈 다시 — 4 + 4 + 8(sub-params: anchor_ratio, v_t_floor, w_rep, r_score_minimum, i_completeness_minimum, v_s_base, n_threshold, late_round_aggression_modifier) = 16. 그 위에 w_info(derived 1) + market 공통(3) = 20 - 1 derived - 3 공통 = 16 명시.

핵심: 4 프리셋(Hunter/Closer/Verifier/Balancer) × 16 명시 fields = 새로 결정해야 할 값 64개. 단 weights 합=1 제약 → 사실상 자유도는 그보다 적음.

왜 market 3개만 공통?

  • gamma / market_utilization / cross_pressure_sensitivity는 "시장 데이터(다른 listing 가격 등)를 얼마나 참고하는가"를 결정. 협상 스타일(공격적/신중함)과 직교하는 별도 axis.
  • 사용자가 "이 에이전트는 시장 잘 본다 / 못 본다"를 페르소나로 인식하기 어려움.
  • LLM tuning 다음 sprint에서 — 사용자가 "쿠팡/네이버 시장가 자주 봐줘" 같은 발언 하면 그때 조정.

4. 레이더에 무엇을 보여줄지

이전 8-stat 시스템(폐기 중)의 레이더

옛 레이더 8axis: anchoring / tenacity / resolve / market_sense / risk_radar / scrutiny / patience / rapport.
이건 사용자 입력 dimensions(stat)이고, 함수가 17 EngineParameters로 변환했다. 폐기.

새 시스템에서 레이더 갯수 옵션

옵션축 갯수축장단
4각형 4 w_p / w_t / w_r / w_s 가장 단순. 단 프리셋 차이가 평평하게 보임 (curve, sub-param 안 보임)
8각형 (추천) 8 w_p / w_t / w_r / w_s · alpha / beta / u_threshold / u_aspiration 차원 가중치 + 행동 곡선 모두 한눈에. 이전 시스템과 axis 갯수 동일 (시각 일관성)
16각형 16 위 8 + sub-params 8 가장 정보 풍부. 단 너무 세밀해 사용자 머리 아픔. 작은 카드(88px)에 안 들어감

추천: 8각형

  • 사용자 인식 가능한 dimension만 (curve도 "양보 빠름/느림" 같은 직관 있음)
  • sub-params는 weight + curve가 결정된 다음 따라가는 second-order — 레이더에 안 보여도 OK
  • 작은 카드 자리에도 들어감 (88px)

5. Advanced Settings — 유저가 만질 수 있는 것

"고급 사용자가 직접 슬라이더로 만지고 싶다"면 — 옵션 C 기준 16개 명시 필드 전부 만질 수 있어야 의미 있다. 그러나 그 중 직관적인 것과 너무 internal한 것 구분 필요:

티어필드UI 요소
Tier 1
(directly intuitive)		 w_p, w_t, w_r, w_s 4개 슬라이더, 합=1 normalize (다른 거 움직이면 자동 조정)
Tier 2
(behavioral)		 alpha, beta, u_threshold, u_aspiration 4개 슬라이더, 각자 envelope 안에서 독립. 라벨 풀어 쓰기 ("시간 압력 강도", "양보 속도" 등)
Tier 3
(fine-tuning, expert)		 anchor_ratio, v_t_floor, w_rep, r_score_minimum, i_completeness_minimum, v_s_base, n_threshold, late_round_aggression_modifier 접힌 섹션(Expand 토글). 슬라이더 + 짧은 설명 툴팁
안 보임 gamma, market_utilization, cross_pressure_sensitivity NEUTRAL 고정. UI에서 빼거나 read-only로
안 보임 (자동) w_info w_rep 슬라이더 옆에 "= 1 - w_rep = 0.45" 같은 read-only 표시

추천 UX

  1. 기본 화면: Tier 1 + Tier 2 (8개 슬라이더) — 8각형 레이더와 1:1 대응
  2. "Expert mode" 토글: Tier 3 (8개 슬라이더 추가) — 16개 슬라이더 총합
  3. 모든 슬라이더는 자기 envelope 안에서 자유 (다른 필드 영향 X). 단 weights 4개만 합=1 normalize

6. 400 budget vs envelope — 왜 더는 budget 필요 없는가

이전: 400 budget 시스템 (폐기 중)

옛 8-stat 시스템에서:

  • 각 stat: [10, 90] 범위 정수
  • 8개 stat 합: 정확히 400
  • 의미: "한 stat 올리면 다른 stat 내려가야 함" — 제로섬 budget
  • 이유: 사용자가 무한히 강한 캐릭터를 만들 수 없게. RPG 스탯 할당과 같은 컨셉

새 시스템: envelope 시스템

각 필드가 자기 고유한 valid range(envelope)를 가짐:

weights:        합 = 1.0 (자체 budget — 자연스러운 비율)
alpha:          0.3 ~ 3.0
beta:           0.3 ~ 3.0
u_threshold:    0.3 ~ 0.85
u_aspiration:   0.3 ~ 0.85  (단 u_aspiration > u_threshold)
anchor_ratio:   0 ~ 1
v_t_floor:      0 ~ 1
w_rep:          0 ~ 1
r_score_minimum:        0 ~ 1
i_completeness_minimum: 0 ~ 1
v_s_base:       0 ~ 1
n_threshold:    5 ~ 15 (integer)
late_round_aggression_modifier: 0.5 ~ 1.5

핵심 차이

옛 400 budget새 envelope
제약합 = 400 (cross-field)각자 자기 범위 안 (per-field) + weights만 합=1
한 필드 올리면다른 필드 내려가야 함독립적 — 아무 영향 X (weights 제외)
"강한 캐릭터" 방지budget으로 강제각 envelope 자체가 sensible 범위 → 자연스럽게 사실적
RPG 느낌강함 — 스탯 할당약함 — 그냥 설정값들

왜 더는 budget 필요 없는가

  • 각 envelope이 이미 "비현실적 값"을 막아줌 (예: beta=10이면 너무 빨리 양보, 엔진이 미친 행동 → envelope 0.3~3.0이 그걸 방지)
  • weights는 자체 budget(합=1) 있음 — 한 차원 강조하면 다른 거 자연스럽게 줄어듦
  • 나머지 필드들은 서로 독립이 자연스러움. 예: u_threshold(까다로움)과 anchor_ratio(앵커 강도)는 동시에 둘 다 높을 수 있음 (까다로우면서 강한 앵커 — 진짜 사람도 그럼)
  • cross-field budget을 강제하면 오히려 부자연스러운 trade-off 생김 ("앵커 강하게 하려면 까다로움 포기?" — 협상 행동에 안 맞음)
결론: 옛 400 budget은 8-stat 시스템 특유의 RPG 시각화 도구. 새 envelope 시스템에서는 불필요. weights 4개의 합=1 제약은 자연스러운 "비율 분배" — 이건 유지.

한 줄 요약

옵션 C 결정 사항:
  • 엔진 17 fields 중 16개 프리셋별 명시 (w_info 1 derived)
  • market 3개(gamma/market_utilization/cross_pressure_sensitivity)만 NEUTRAL 공통
  • 레이더는 8각형 (weights 4 + curves 4) 추천
  • Advanced Settings는 3-tier: 기본 8개 슬라이더 + Expert로 8개 더
  • budget 제약 없음 — envelope만 사용. weights 4개만 합=1
  • 4 프리셋 × 16 fields = 64개 값을 새로 결정해야 함 (디폴트값 채우는 작업 별도 필요)
