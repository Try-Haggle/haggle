- `HaggleDisputeBondEscrow`가 구매자·판매자 USDC를 거래대금과 별도 보관한다. 운영자는 양측 입금을 확인한 뒤에만 심사를 시작한다. 완료된 단계의 패소자 비용만 보류하고 승소자 및 미실시 단계 예치금은 각 단계의 납부 지갑으로 반환한다. 수수료 출금은 소유자의 별도 행동이며 API에서는 호출하지 않는다.
- API는 양측 예치 전 리뷰어 배정·투표·일반 판결을 막는다. 판매자만 기한까지 미예치했고 구매자 예치가 확인되면 관리자가 별도 종료 경로로 구매자 승소를 기록한다. 자동 만료 작업은 대사 대상만 알리고 금전을 이동시키지 않는다. T3 미개시 종료는 기존 T2 비용만 유지한다.
- 결제 화면은 연결된 당사자 지갑에서 USDC 승인과 예치 확인을 요청한다. mock 예치는 비운영 환경에서만 허용한다. 같은 사건·단계의 결제 수단 혼합은 거부한다.

## 2026-09-27 정산 정책 문서 변경

정행의 요청으로 [정산 설계 6·7절](../features/분쟁_시스템_v2.md)과 두 디자인 문서를 맞췄다.
이 항목은 문서 변경이며 아래 2026-09-26 임시 구현의 자금 흐름을 변경하거나 검증한 것은 아니다.

- 최종 승소자의 분쟁 비용은 $0. 판매자 승소 시 거래대금 전액, 구매자 승소 시 대금 전액 환불이며 자기 심사비 담보는 모두 반환한다.
- 구매대금과 판매자 보증금은 스마트 컨트랙트 예치가 목표다. 구매자 패소비를 대금에서 빼지 않으려면 구매자 심사비 재원도 별도로 확보해야 한다.
- 양측 T2/T3 심사 전 별도 보증금 예치를 확정 정책으로 기록했다. 구매자 보증금은 기존 구매대금에 추가되는 금액이며, 최종 패소자의 보증금으로 심사비를 충당한다.
- 필요한 예치 확인 → 리뷰어 배정·심사 순서. 구매자 예치 후 판매자 미예치 종료는 해당 미실시 단계 심사비·리뷰어 보상·플랫폼 배분 $0이며 구매자 해당 단계 담보를 반환한다.
- T3 미예치로 이전 T2 보수를 지우지 않는다. 이미 맡긴 리뷰는 미실시로 취급하지 않으며 재원 부족을 승소자에게 전가하지 않는다.
- 비용 누적/최종 단계 대체, T3 번복 시 이전 단계 보수·DS 처리, 구매자/양측 미납 규칙은 미결정으로 남긴다. 담당자를 임의로 추가 배정하지 않는다.

**후속 구현 선행 조건:** 단계 간 요금·담보 정책 확정, 실제 온체인 담보·보상 지급·최종 승소자 환급 설계와 법적 검토.
그 전에는 이 문서 변경을 근거로 실자금 정산을 활성화하지 않는다. 검증 시 $500 대금 + 양측 $12 담보의 구매자 승소/판매자 승소($524 보존), 판매자 미예치($512 전액 구매자 반환), T3 미예치 시 T2 보수 보존을 각각 확인한다.
기존 `pnpm work:me -- "정행"` 조회는 무관한 `W2026-08-31-01`의 리뷰어 미지정 오류로 실패한다. 본 작업은 그래프의 `W2026-08-08-01` 담당 정행·리뷰어 인오(`proposed`)를 직접 확인했고 배정·완료 상태는 바꾸지 않았다.

문서 검증: `git diff --check`, 그래프 JSON 파싱·담당/리뷰어/상태 보존, 정산 설계 상대 링크, 예시의 입출금 합계($524/$512)를 확인했다. 문서의 기존 원금 차감·$488 지급 예시도 제거했다. 이번 문서 변경으로 코드·DB·컨트랙트를 수정하거나 실행 검증한 것은 아니다.

### T2/T3 구현 조사

기존 코드는 분쟁 생성, 증거 보관·검사, AI 평가·운영자 승인, 비용·보증금 계산,
리뷰어 자격시험, 배정·투표·집계 API, 환불 finalizer를 이미 포함했다.
설계 문서의 “DB/API 연동은 Phase 3에서 진행”이라는 표시는 실제 코드보다 오래됐다.

T2/T3는 핵심 계산과 API 골격이 있었지만 실제 사용 흐름은 연결되지 않았다.

| 발견한 문제 | 이번 수정 |
|---|---|
| 배정에 tier가 없어 T2 투표가 T3 집계에 섞임 | 배정에 tier 저장, 집계와 투표를 현재 tier로 제한 |
| 기존 리뷰어를 다시 뽑으면 unique 충돌, 재시도 시 중복 배정 | 해당 분쟁의 모든 기존 리뷰어와 당사자를 제외하고 부족 인원만 보충 |
| 승급 시 이전 심사 완료 여부·최종 종료 상태를 검사하지 않음 | 완료된 T1 또는 T2에서만 한 단계 승급, T3가 마지막 |
| 화면이 승급 응답에 없는 `dispute`를 읽음 | API가 갱신된 분쟁을 반환하며 화면도 실제 계약 사용 |
| `UNDER_REVIEW`일 때 승급 버튼이 숨겨짐 | 완료된 심사에 한해 다음 단계 버튼 노출 |
| 리뷰어 화면이 실제 API와 다른 응답 구조 및 `vote_pct` 사용 | 실제 중첩 응답과 `vote`, `expected_tier` 사용 |
| 대시보드가 API에 없는 상태 필드로 모든 배정을 숨김 | 서버가 배정 tier·active/voted/decided를 반환 |
| 투표 후 active slot이 해제되지 않음 | 투표와 슬롯 반환을 같은 transaction에서 수행 |
| 자격시험 화면의 문제와 서버 채점 문제가 다름 | 서버 문제 목록을 조회하고 case_index/vote로 제출 |
| 파일 증거를 리뷰어가 열 수 없음 | 배정 확인 및 분쟁 경로 검증 후 기존 private storage 서명 URL 발급 |
| T3에서 판매자 보증금을 다시 생성함 | 임시 코드에서는 동일한 거래액 전액 담보를 이어 사용하며 종료된 담보는 거부. 2026-09-27 목표 심사비 담보 정책과 다르므로 후속 교체 필요 |

## 사용자 결과

1. T1 AI 평가가 완료되면 당사자는 사유와 다음 단계 비용을 확인하고 T2를 요청한다.
2. 임시 코드는 서버가 거래액에 맞는 패널을 배정한다. 인원이 부족하면 부족한 상태 그대로 표시한다. 목표 설계의 양측 심사비 담보 확인 전 배정 차단은 아직 필요하다.
3. 배정된 리뷰어는 양측 증거를 읽고 0–100 투표와 이유를 제출한다.
4. 필요한 인원이 모두 투표해야 권고 결과가 나온다. T2 결과에 불복하면 T3를 요청한다.
5. T3는 기존 리뷰어를 제외한 새 패널로 시작한다. 이전 판단과 승급 사유는 기록에 남는다.
6. 최종 정산은 기존 관리자 resolve/finalizer 경로다. 투표·집계·승급 자체로 돈을 옮기지 않는다.

기존 디자인 시스템의 Button, Alert, Badge, Field, Textarea, VoteSlider, EvidenceCard,
BackLink와 semantic color token을 재사용했다. 서버에 없는 판례·예상 보상·DS 변화·투표
분포를 실제 결과처럼 표시하던 화면 항목은 제거했다.

## 동시성·금전 경계

- 승급, 배정, 투표, 집계는 해당 dispute row의 `FOR UPDATE` 잠금을 같은 순서로 취한다.
- 성공 응답은 transaction이 끝난 뒤 반환한다. 배정 실패 시 단계·담보 생성도 rollback된다.
- 승급은 resolve와 같은 operation lease를 사용한다. stale `expected_tier` 요청은 409다.
- T2→T3는 저장된 완료 상태 외에도 현재 tier의 quorum을 다시 계산한다.
- resolve도 현재 패널 quorum과 outcome/refund 금액 일치를 검사한다.
- 단일 리뷰어의 중복 표는 dispute-core에서도 거부한다.
- 리뷰어 파일 조회는 assignment, evidence의 dispute ID, 저장소 경로, retention 상태를 확인한다.

## DB 적용과 병합 순서

`0157_reviewer_assignment_tier.sql`은 배정 tier, check constraint, 조회 인덱스를 추가한다.
기존 데이터는 tier를 복원할 근거가 없으므로 T2로 보존한다. 기존 T3 집계 metadata는
무효화하고 새 T3 패널을 배정해야 한다. 과거 투표가 잡고 있던 active slot도 재계산한다.

**같은 SHA의 최종 CI 성공 전에 공유 DB에 migration을 적용하지 않는다.**
이번 작업에서는 공유 DB에 적용하지 않았다. migration을 먼저 적용한 뒤 이 API를 배포해야 한다.
`reviewer.ts`, `disputes.ts`, reviewer assignment schema와 응답 계약 변경은 이 slice와
겹치므로 후속 변경은 이 slice 뒤에 병합한다. 이전 웹의 vote_pct 요청은 이미 동작하지 않던
계약이며, 새 웹/API를 함께 릴리스한다.

## 남은 조건과 판단

- 인오의 reviewer confirmed 및 판단이 필요하다. 임의로 다른 리뷰어에게 배정하지 않는다.
- CI 후 migration 적용, 실제 리뷰어 풀·두 당사자 계정·private evidence로 staging 리허설.
- 운영자가 `POST /disputes/:id/assign-reviewers`로 부족 인원만 재배정할 수 있다.
  자동 재배정 job, 미투표자 교체, 심사 기한 만료 처리는 이번 범위에 없다.
- 최종 자금 이동, 실 USDC 담보 수집·환불, reviewer reward/DS accounting의 전체 동작은 별도 검증이 필요하다.
  T3 할인 및 무료 재심 계산 helper도 기존처럼 실제 청구에 연결하지 않았다.
- 기존 자격시험은 MVP의 고정 연습 문제다. 실 판례 무작위 추출·거래수/Trust 자격 확인은 별도 작업이다.
- 심사 중 추가 증거/장시간 AI 재평가와의 동시성, 실제 증거 snapshot 고정 정책은 후속 검토 대상이다.
- 기존 데이터에서 이미 여러 보증금이 만들어진 사건은 자동 병합하지 않았다. staging 적용 전 확인한다.
- 2026-09-27 승소자 무부담·별도 담보·미예치 무심사 종료 정책은 문서만 반영했다. 기존 코드의 거래액 담보·회사 지갑 수집·승급 시 배정·정산식을 이 목표 정책과 혼동하지 않는다.

리뷰 판단: 이전 표가 새 패널에 섞이지 않는지, 돈을 움직이지 않는 심사와 최종 정산이 분리되는지,
부족한 리뷰어를 완성된 패널로 표시하지 않는지, migration 전후 기존 사건 보존 방식이 적절한지 확인한다.
