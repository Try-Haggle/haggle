Group 1 · 👤 사람 1

그룹 1 — 결정부: 엔진이 가격·수락을 결정

이 그룹 = "가격·수락을 LLM 대신 엔진이 결정하게 만들기" (LLM은 작가). 지금은 LLM이 최종가를 덮어써 모델·요청마다 흔들림(decide.ts:84) → 엔진이 확정(결정론). 흐름: 컨텍스트 조립(HAGGLE-1·2·3 = 17파라미터를 엔진에 넘김) → 엔진 결정(computeUtility+makeDecision) + LLM price 제거 → 심판(HAGGLE-10). 짝꿍 그룹2와는 H6에서만 합류.

⚠️ 이 그룹만으로는
엔진이 숫자(target/floor/시간/신뢰)로만 결정 → 상대의 자연어 주장("배터리 89%라 깎아줘")은 아직 가격에 안 먹힘. 그건 그룹 2(센서부)가 채웁니다.
1HAGGLE-1 · 파라미터 대부분 사장 (17개 중 2개만 작동)🔴 높음🟠 큼아직 할 일
문제
사용자가 프리셋·슬라이더·빌더챗으로 튜닝하는 EngineParameters 17개 필드 중 실제 협상에 반영되는 건 beta·anchor_ratio 2개뿐. 나머지는 저장만 되고 아무도 안 읽는다. 즉 UI로 아무리 튜닝해도 대부분 무시된다. 하이브리드(엔진이 파라미터로 결정)의 핵심.
개념 — 축 vs 성향 vs 상황 (헷갈리기 쉬움)
"17개를 4개로 좁힌다"가 아니다. 4개 축(가격·시간·위험·관계)=딜 평가 기준 · 17개 파라미터=내 성향(각 축을 얼마나 중시/어떻게 채점, 고정) · 컨텍스트=이 딜의 상황(매 라운드). U_total=w_p·V_p+w_t·V_t+w_r·V_r+w_s·V_s. 17개 성향은 4축에 배분(가격:anchor_ratio·gamma / 시간:alpha·v_t_floor / 위험:w_rep·w_info / 관계:v_s_base·n_threshold)되고, beta·u_threshold는 축이 아닌 전역 손잡이. 이 티켓 = "각 축에 컨텍스트(사실)를 채워 엔진이 17개 성향으로 점수를 내게 하는 것".
현재 동작 (코드 근거)
  • 런타임에서 strategy_params를 읽는 코드는 anchor_ratio·beta 뿐default-engine-skill.ts:75,99 · coach.ts
  • weights는 추출되나 coach가 하드코딩 가중치로 덮어 무시coach.ts:163
  • alpha·v_t_floor·u_threshold·u_aspiration: 읽는 코드 0건. extractStrategyParams가 7개만 추출memory-reconstructor.ts
목표
사용자가 고른 파라미터가 실제 협상 행동(추천가·수락 기준·시간/위험 태도)에 반영된다.
완료 기준
프리셋/슬라이더를 바꾸면 동일 상황의 협상 결과가 실제로 달라진다(회귀 테스트로 고정). 어느 필드가 어디에 영향을 주는지 문서화.
손볼 곳
memory-reconstructor(추출 확대) + coach/decide(소비) · 또는 근본해법: 매 라운드 NegotiationContext 조립 → engine-core computeUtility/makeDecision 재연결
의존
#0 하이브리드 결정 시 근본해법(engine-core 재연결)이 정답에 가까워짐. §SOT 4.4 참고.
