협상 엔진, 처음부터 끝까지

이 엔진을 처음 보는 개발자를 위한 문서입니다. 에이전트가 어떻게 만들어지고 → 그 설정이 협상에 어떻게 반영되고 → 매 라운드 무엇이 수학적으로 계산되고 → LLM이 어떤 데이터를 받아 무슨 프롬프트로 무엇을 결정하는지를, iPhone 협상 한 건으로 실제 숫자를 따라가며 봅니다.

목표는 단순 사용법이 아니라 전체 과정을 정확히 이해해서 "더 나은 방법이 없을까"를 고민할 수 있게 하는 것입니다. 그래서 각 단계에서 실제로 도는 것 vs 형식적으로만 있는 것을 정직하게 구분합니다.

읽는 렌즈: 무엇 데이터·필드 · 수학 계산 · LLM 모델이 받는 것/하는 것. 자세한 근거는 항상 SOT 레퍼런스로 링크.
📂 코드 인용 표기 — 데모/프로덕션 구분
이 문서의 코드는 전부 실제 저장소에서 가져왔고, 블록마다 출처 파일과 성격을 답니다: 🟢 프로덕션 실전 협상 경로 · 🟡 데모·테스트 실전 미사용 · ⚪ 예시 설명용 값(구조는 실제). 이 페이지는 데모 파일(scripts/demo-*.ts 등)에서 가져온 코드가 없습니다 — 전부 프로덕션 경로거나 예시입니다.

Part 0

먼저 알아야 할 3가지

이 3개를 모르면 코드가 통째로 오해됩니다. 나머지는 전부 이 위에 얹힙니다.

1
협상은 AI vs AI 자동재생이다
유저가 "협상 시작"을 누르면(POST /negotiations/start), 서버가 구매자·판매자 양쪽 AI 에이전트를 만들어 한 요청에서 협상 전체를 끝까지 자동으로 돌립니다. 사람이 라운드마다 개입하지 않습니다. (외부 에이전트가 오퍼를 하나씩 넣는 /offers 경로도 따로 있음.)
2
가격은 LLM이 정하고, 엔진은 코치+심판이다
"엔진이 두뇌"라는 상식과 반대입니다. 순수 수학 엔진은 추천가를 계산(코치)하고 규칙을 검증(심판/Referee)할 뿐, 실제 가격·메시지는 LLM(grok)이 작성합니다.
3
상태는 4계층으로 흐른다
EngineParameters(성향) → MasterStrategy(성향+이 거래 가격) → negotiation_sessions(살아있는 상태) → CoreMemory(매 라운드 재조립되는 작업본). 같은 데이터가 옷을 갈아입습니다.

한 장 그림

유저 설정 → 협상 시작 → auto-play 루프(CoreMemory→코치→LLM→Referee) → 결과

아래 Part 1~5가 이 그림의 각 상자를 실제 데이터로 확대합니다.

Part 1 · 무엇

에이전트가 만들어진다 — EngineParameters

유저는 프리셋을 고르고, 필요하면 슬라이더/빌더챗으로 튜닝합니다. 방법이 뭐든 결국 단 하나의 폼 EngineParameters로 모입니다. 이게 에이전트의 "성향"입니다. (가격은 아직 없음 — 성향은 여러 매물에 재사용.)

예시: 판매자가 "가격 사냥꾼(hunter)" 프리셋 선택

🟢 프로덕션packages/shared/src/agent-presets/negotiation-agent-presets.ts· 실제 프리셋 값
// EngineParameters — hunter 프리셋 { "weights": { "w_p":0.5, "w_t":0.15, "w_r":0.2, "w_s":0.15 }, // 가격 중시 50% "beta":0.4, // ★ 양보 속도 — 낮을수록 고집 (막판까지 버팀) "anchor_ratio":0.5, // ★ 오프닝 앵커 강도 — 낮을수록 공격적 "u_threshold":0.55, "u_aspiration":0.7, "v_t_floor":0.7, "alpha":0.5, … }

그리고 빌더챗에 "IMEI 확인 필수, 안 급해"라고 적으면 → builderChatMemory: { dealBreakers:["IMEI verification required"], urgency:"low" }가 붙습니다.

필드의미★ 실제 영향?

Part 2 · 무엇→어디

필드가 협상 전략이 된다 — 컴파일

협상이 시작되면 컴파일러가 성향 폼 + 이 거래의 리스팅(가격·마감)을 합쳐 MasterStrategy 스냅샷을 만듭니다. 이게 세션에 저장돼 협상 내내 불변입니다.

🟢 프로덕션packages/engine-session/src/strategy/compiler.ts · compileNegotiationAgentSnapshot()
성향 폼 + 이 거래의 리스팅 → 하나의 MasterStrategy 스냅샷 (세션 내내 불변)
🔑 왜 "2개만 작동"인가 — 여기가 핵심
컴파일러는 파라미터를 손실 없이 스냅샷에 다 넣습니다. 문제는 그 다음입니다. 매 라운드 스냅샷에서 값을 꺼내 쓰는 StrategyParams 추출기가 7개만 뽑고, 그중에서도 실제 계산에 쓰는 코드가 있는 건 beta·anchor_ratio 뿐입니다. 나머지는 스냅샷에 저장만 되고 아무도 안 읽습니다.

Part 3 · 런타임

협상이 돌아간다 — auto-play와 라운드 루프

/start는 구매자·판매자 스냅샷을 둘 다 만들고, 루프를 돌며 매 라운드 세션의 "관점(역할·스냅샷)"을 교체하면서 executor를 호출합니다. 한 요청 안에서 협상이 끝까지 재생됩니다.

🟢 프로덕션apps/api/src/routes/negotiations.ts· /start 루프 (가독성 위해 요약)
// /start 자동재생 루프 (요지) for (라운드 i = 0 … MAX) { setSessionPerspective(이번에 응답할 역할, 그 역할의 스냅샷) // 관점 교체 result = executeStagedNegotiationRound(session, 이번 오퍼, …) // 한 라운드 if (타결 || 결렬 || 무효) break 다음 오퍼 = result.outgoingPrice ; 역할 교대 }

한 라운드가 하는 일 (executor)

상대 오퍼가 들어오면 세션 상태에서 이번 라운드에 필요한 값만 뽑아 CoreMemory로 재조립하고, 6단계 파이프라인을 돕니다.

Part 4 · 수학

수학이 값을 만든다

이 라운드에 실제로 도는 계산은 셋입니다. 가격을 만드는 건 ① 하나이고, 나머지는 참고용입니다.

💡 읽는 법 수식이 나와도 겁먹지 마세요. 각 수식 옆에 💡 쉽게 말하면 상자로 우리말 설명을 붙였습니다. 기호가 안 와닿으면 💡만 읽어도 충분합니다.

① Faratin 양보 곡선 — 추천가를 만든다 ✅ 실제 사용

"시간이 갈수록 마지노선 쪽으로 양보한다"를 한 줄로 모델링합니다. 코치가 이걸로 "이번엔 얼마 부를까"를 계산해서, LLM에게 "이 값 근처로 불러라"는 기준값(=앵커)으로 건넵니다.

💡 쉽게 말하면 협상 초반엔 목표가(내가 받고 싶은 값)를 고집하다가, 시간이 갈수록 마지노선(이보다 나쁘면 안 파는 값) 쪽으로 조금씩 내려주는 곡선이에요. β(베타)라는 숫자 하나가 "얼마나 버티느냐"를 정합니다 — 낮으면 끝까지 버티고, 높으면 초반부터 잘 깎아줍니다.
🟢 프로덕션packages/engine-core/src/decision/faratin.ts· computeCounterOffer (코치가 import) · 계산 예시
추천가 = 목표가 + (마지노선 − 목표가) × 진행도^(1/β)
목표가내가 받고 싶은 값 (예 $500)
마지노선이보다 나쁘면 안 파는 값 (예 $430)
진행도협상이 얼마나 지났나 — 0=시작, 1=마감
β (베타)버티는 정도 — 낮으면 끝까지 버팀, 높으면 잘 깎아줌
// 판매자: 목표 $500, 마지노선 $430, 진행도 = 8라운드 중 2번째 = 0.25, β = 0.4(hunter) 추천가 = 50000 + (43000 − 50000) × 0.25^(1/0.4) = 50000 − 7000 × 0.031 ≈ $497.8 // 거의 안 내림 = 고집 // 만약 β=2.0(closer)이었다면? 50000 − 7000×0.5 = $465 (훨씬 양보)

이게 "성향이 가격을 바꾼다"의 실제 증거. 같은 상황·같은 시점인데 β 한 숫자로 $497.8 vs $465로 갈립니다. → SOT §6.2

② 상대방 양보율 — EMA ✅

상대가 라운드마다 얼마나 값을 움직여주는지를 추적해 BOULWARE(잘 안 물러남)/LINEAR(꾸준히 양보)/CONCEDER(잘 깎아줌)로 분류합니다. LLM 프롬프트에 "이 상대는 이런 타입"이라는 힌트로 들어갑니다.

💡 쉽게 말하면 상대가 매번 얼마나 깎아주는지 지켜보면서 "이 사람 잘 안 물러나네 / 잘 깎아주네"를 판단합니다. EMA는 그 평균을 낼 때 오래된 것보다 최근 행동에 더 무게를 두는 방식이에요(0.3=이번 것 비중, 0.7=지금까지 비중).
🟢 프로덕션apps/api/src/negotiation/memory/memory-reconstructor.ts · referee/coach.ts
ema ← 0.3 × 이번 양보율 + 0.7 × 이전 ema
ema상대의 평균 양보율 — 매 라운드 갱신되는 값
이번 양보율이번 라운드에 상대가 값을 얼마나 움직였나
0.3 / 0.7이번 것 비중 / 지금까지 비중 — 최근에 더 무게
// ema로 상대 유형 분류 (2라운드부터) ema < 0.005 → BOULWARE(잘 안 물러남) · ema > 0.05 → CONCEDER(잘 깎아줌) · 그 외 → LINEAR

③ 효용 점수 — "이 딜이 나한테 얼마나 좋은가" 🚧 참고용

💡 쉽게 말하면 "이 거래가 나한테 얼마나 좋은가"를 0~1 사이 한 점수로 요약한 겁니다. 가격만 보는 게 아니라 가격·시간·신뢰·관계 네 가지에 각각 점수를 매기고, 각각이 얼마나 중요한지를 곱해서 더합니다.
🟢 프로덕션(코치)apps/api/src/negotiation/referee/coach.ts:163
U_total = w_p·V_p + w_t·V_t + w_r·V_r + w_s·V_s
U_total이 거래 총점 — 0~1, 높을수록 좋은 딜
V_p V_t V_r V_s각 항목 점수(0~1) — 순서대로 가격·시간·신뢰·관계
w_p w_t w_r w_s각 항목 중요도(가중치) — 다 더하면 1
w · V중요도 × 점수, 그걸 네 항목 다 더한 게 총점
🔍 몰라도 되는 디테일: '가격 점수(V_p)'는 마지노선에 가까울수록 1달러를 더 크게 느끼도록 로그라는 곡선을 씁니다. 지금은 그냥 넘어가도 됩니다.
그런데 — 지금은 이 점수가 결정에 안 쓰입니다
실제 가격은 ①Faratin이 정하고, 이 효용 점수는 참고용으로만 흐릅니다. 게다가 사용자가 고른 '중요도'가 아니라 고정된 값(0.5 / 0.2 / 0.15 / 0.15)을 씁니다. 가장 정교한 계산이 정작 안 쓰이는 것 — 이게 큰 개선 후보입니다(Part 7).

Part 5 · LLM

LLM이 결정한다 — 데이터·프롬프트·역할

가장 중요한 부분입니다. LLM(grok-4-fast)은 코치가 만든 추천가 + 경계값 + 전략(빌더 메모리) + 종료 힌트를 압축 프롬프트로 받아, 실제 가격과 상대에게 보낼 메시지를 작성합니다.

LLM이 받는 데이터 (무엇이 프롬프트에 실리나)

블록내용출처
LISTING제목·카테고리·상태·속성(배터리·저장용량 등)listing_context
STRATEGYpersona + 빌더 메모리(tone·urgency·dealBreakers·mustEmphasize…)strategy_context
S:/B:/C:상태 / 경계(target·floor·내오퍼·상대오퍼·gap) / 추천가·tactic·상대패턴CoreMemory + 코치
HIST·OPP_SAID지난 라운드 가격들·상대의 마지막 말라운드 로그
NEGOTIATION_HINTgap이 작으면 서버가 "ACCEPT하라"를 직접 주입encodeClosingHint
🔎 놀라운 사실 — 숫자 파라미터는 프롬프트에 안 들어간다
STRATEGY 블록은 persona와 빌더챗 메모리(자연어)만 넣습니다. weights·alpha·u_threshold 같은 숫자 성향은 프롬프트에 아예 안 실립니다. 즉 LLM에 닿는 유일한 "성향 신호"는 빌더 메모리(dealBreakers 등)와, 코치가 β로 계산한 추천가뿐입니다.

to your floor — concessions are earned, not given.

## How to negotiate like a real person
1. READ what the opponent just said. If they made an argument (condition, market price, urgency), engage with it.
2. JUSTIFY your move with one concrete signal from the LISTING or your STRATEGY.
3. CONCEDE proportionally. If the opponent moved toward you, move toward them — by less than they did.
4. ACCEPT when the offer is at or better than your target, or the gap is small and you are running out of rounds.
5. Keep messages to 1–2 short sentences. Match the tone in STRATEGY...

## Reading the compact memo
In "B:t$X/f$Y/c$Z/o$W": t = YOUR target, f = YOUR floor (hard limit), c = YOUR last offer, o = OPPONENT's last offer.
