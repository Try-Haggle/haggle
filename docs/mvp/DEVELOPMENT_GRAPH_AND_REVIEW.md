# Haggle 개발 그래프와 리뷰 운영

**상태:** Active

**시행일:** 2026-08-12

**대상:** 토요일 주간 회의, feature 개발, staging 통합, 릴리스 후보 검증

모든 기여자가 따라야 할 실제 작업 순서는 저장소 루트의
[CONTRIBUTING.md](../../CONTRIBUTING.md)에 정의한다. 이 문서는 그래프 구조와 리뷰·검증 정책의 상세
근거다.

## 1. 여기서 말하는 그래프 엔지니어링

Haggle의 개발 그래프는 그래프 DB를 도입한다는 뜻이 아니다. 사람, 작업, 리뷰, 선행 조건,
검증 증거를 서로 연결해 다음 질문에 바로 답할 수 있게 만드는 운영 방식이다.

- 내가 이번 주에 끝내야 할 일은 무엇인가?
- 내가 리뷰해야 할 일은 무엇이며, 무엇을 판단해야 하는가?
- 내 작업은 누구의 어떤 작업을 기다리는가?
- 내 작업이 늦어지면 누가 막히는가?
- 아직 담당자가 확실하지 않은 일은 무엇인가?

현재 주의 단일 소스는 `docs/meetings/current-week-work-graph.json`이다. 사람과 작업이 노드이고,
`ownerId`, `reviewerId`, `dependsOn` 참조가 간선이다. 별도의 그래프 서버 없이도 검증·조회할 수
있으며, 필요해질 때 같은 구조를 GitHub Projects나 그래프 DB로 옮길 수 있다.

## 2. 고정 규칙

1. 각 작업에는 구현 담당자 한 명과 그 사람이 아닌 리뷰어 한 명만 둔다.
2. 보호 영역도 리뷰어를 추가하지 않는다. 그 위험을 판단할 수 있는 한 사람을 단일 리뷰어로 고른다.
3. 회의 녹음에서 담당자가 명확하지 않으면 추측하지 않고 `unassigned`로 남긴다.
4. 리뷰어 변경 시 주간 그래프와 작업 카드에 이유를 기록한다.
5. 리뷰는 모든 코드를 한 줄씩 다시 읽는 일이 아니다. 사용자 결과와 위험, 검증 증거를 먼저 판단하고
   그 판단에 필요한 코드 경계만 확인한다.
6. 주간 그래프의 배정은 회의에서 사람이 확인한 뒤 확정한다. 녹음 분석은 초안 생성 수단이지 최종
   의사결정자가 아니다.

## 3. 주간 운영 흐름

```text
토요일 20:00 또는 20:30 회의
  → 녹음·회의 메모에서 사람/작업/의존성 후보 추출
  → 담당이 명확한 작업만 owner 확정
  → 작업마다 단일 reviewer 확정
  → 불명확한 작업은 unassigned로 보존
  → current-week-work-graph.json 갱신·검증
  → feature 브랜치 구현 및 자동 검사
  → 설명 중심 PR 브리핑과 지정 리뷰어 승인
  → staging 통합·Playwright·보안 검사·사용자 흐름 리허설
  → 릴리스 후보 SHA 고정
  → 8월 22일 직전 staging → main Deploy PR
```

회의는 보통 토요일 20:00 또는 20:30에 진행한다. 정확한 시작 시각과 시간대는 매주 회의 공지에서
확정하고 그래프의 `meeting`에 기록한다.

## 4. 회의에서 기록할 내용

각 작업에 다음을 평문으로 합의한다.

1. 사용자가 얻게 될 결과
2. 구현 담당자 한 명
3. 작성자와 다른 리뷰어 한 명
4. 이번 주의 다음 행동과 완료 조건
5. 선행·후속 작업
6. 자동 검사, Playwright, staging 등 필요한 증거
7. 리뷰어가 코드보다 먼저 판단해야 할 질문
8. 가장 위험한 실패와 복구 방법

담당자 발언이 약하거나 서로 다른 해석이 가능하면 빈칸을 사람 이름으로 채우지 않는다. 그 작업은
`ownerId: null`, `reviewerId: null`, `status: "unassigned"`로 남기고 다음 회의의 확인 항목으로 보여준다.

## 5. 리뷰어 한 명을 고르는 기준

다음 순서로 고른다.

1. 구현 담당자와 다른 사람인가?
2. 변경 결과를 직접 소비하거나, 실패를 가장 잘 발견할 수 있는 사람인가?
3. 결제·인증·DB·스마트 계약·배포처럼 보호 영역이면 해당 위험을 판단할 수 있는가?
4. 현재 작업과 충돌한다면 병합 순서와 의존성을 함께 확인할 수 있는가?
5. 특정 사람에게 리뷰가 몰리지 않는가?

| 변경 영역 | 단일 리뷰어가 판단할 핵심 |
|---|---|
| Web/UI | 실제 사용자 흐름, 오류·로딩·재시도, Playwright 결과 |
| API/협상 | 호출자 계약, 상태 전이, 멱등성, 실패 응답 |
| DB/마이그레이션 | 기존 데이터 호환성, 동시 배포, 복구 |
| 인증/권한 | 다른 사용자 데이터 접근, 토큰·세션 실패 |
| 결제/정산 | 금액 보존, 소유권, 중복 요청, receipt 검증 |
| 배송/분쟁 | 외부 이벤트 순서, 증거, release 차단 |
| 스마트 계약 | 권한, 자금 이동, invariant, 업그레이드 |
| CI/배포/의존성 | 우회 경로, 동일 SHA, 시크릿, 실패 시 차단 |

## 6. 이름을 말하면 보는 화면

루트에서 다음처럼 실행한다.

```bash
pnpm work:me -- 정행
pnpm work:me -- Sean
pnpm work:me -- Amy
pnpm work:me -- "나는 정행이야"
pnpm work:me -- --all
```

한글 이름, 영어 이름, 회의 파일명에 쓰인 별칭은 같은 사람으로 인식한다. 개인 조회에는 다음이 나온다.

- 이번 주 내가 할 일: 결과, 다음 행동, 기한, 단일 리뷰어, 선행 조건
- 내가 리뷰할 일: 담당자, 리뷰 설명, 확인할 증거
- 내 작업을 기다리는 후속 작업
- 팀이 담당자를 확인해야 하는 미배정 작업

`--all`은 주간 전체 분담과 미배정 항목을 보여준다. 그래프가 규칙을 어기면 조회 전에 실패하므로,
리뷰어가 두 명이거나 참조가 끊긴 상태를 문서에 조용히 남길 수 없다.

## 7. 리뷰 설명 방식

PR 작성자는 `.github/pull_request_template.md`의 리뷰 브리핑을 먼저 완성한다. 리뷰어에게는 다음 순서로
설명한다.

1. 사용자가 새로 할 수 있는 것
2. 변경 전과 변경 후의 흐름
3. 정상 흐름에서 바뀌는 상태와 돈·권한·데이터
4. 실패할 수 있는 지점과 차단 장치
5. 자동 검사와 staging에서 실제 관찰한 결과
6. 이 PR에 의도적으로 포함하지 않은 범위
7. 리뷰어가 결정해야 할 구체적인 질문

파일 수, 함수명, 줄별 구현은 위 설명을 증명할 때만 사용한다. `테스트 통과`만 적지 말고 어떤 행동을
했고 무엇을 관찰했는지 적는다.

## 8. 자동 검증 경로

모든 `staging`/`main` PR과 push는 다음 세 갈래 검사를 통과한 뒤 최종 `CI` 관문으로 모인다.

- 품질: whitespace, 변경 파일 Biome, migration, DB invariant, typecheck, unit/integration test, build
- 브라우저: Playwright public smoke
- 의존성 보안: production dependency audit

새 high와 모든 critical 취약점은 즉시 실패한다. 2026-08-12에 발견된 기존 high 항목은
`.security/audit-baseline.json`에 임시 추적하며 2026-08-17에 만료된다. 이 baseline은 안전 판정이나
영구 예외가 아니다.

공유 DB 마이그레이션은 같은 커밋의 최종 `CI`가 성공한 뒤에만 시작한다. PR 검증에서는 공유 DB를
변경하지 않는다.

Playwright smoke는 브라우저 껍데기를 빠르게 확인하는 최소 관문이다. 인증·협상·결제·배송·정산·분쟁
전체 흐름은 staging 릴리스 리허설에서 별도로 실행하고 점차 자동화한다.

### Git·CI 증거 자동 동기화

GitHub의 브랜치·PR·리뷰·check run·병합과 staging 배포·migration 결과는
[Git·CI 작업 그래프 자동 동기화 계약](../meetings/GIT_CI_GRAPH_SYNC.md)에 따라 작업 ID와 같은 SHA로
연결한다. 현재는 설계만 완료됐으며 workflow가 구현되기 전까지 수동 기록이다.

자동화가 맡는 것은 발생한 기술적 사실의 수집이다. 담당자·단일 리뷰어·의존성·범위·수동 리허설의
판정과 작업 `done`, 최종 릴리스 `GO`는 사람이 결정한다. 따라서 PR 병합이나 CI 성공 하나만으로 작업과
릴리스 게이트가 자동 완료되지 않는다.

## 9. 릴리스와 main

- 개발 기간에는 `main`에 병합하거나 직접 push하지 않는다.
- 모든 feature는 `staging`에서 통합하고 결제까지 전체 흐름을 검증한다.
- 기능 동결 후 하나의 릴리스 후보 SHA를 고정한다.
- 8월 22일 직전 최종 승인에서만 그 SHA의 `staging → main` Deploy PR을 병합한다.
- production 마이그레이션과 배포는 최종 `CI` 성공 및 production 승인 뒤에만 진행한다.
- 8월 22일 범위는 결제 기능까지 포함하지만 실제 가치가 있는 자산과 live provider 활성화는 별도의
  자금 활성화 Go/No-Go를 통과한 뒤 시행한다.

## 10. 매주 확인할 지표

- 리뷰어가 없는 배정 작업 수: 0
- 리뷰어가 둘 이상인 작업 수: 0
- 담당자를 추측해서 넣은 작업 수: 0
- 같은 파일이나 migration을 동시에 소유한 작업 수
- 첫 리뷰까지 걸린 시간과 한 사람에게 몰린 리뷰 수
- CI, Playwright, 보안 검사 실패 원인
- staging에 병합됐지만 사용자 흐름 검증이 없는 작업 수
- 8월 22일 릴리스 후보에 남은 P0 수
